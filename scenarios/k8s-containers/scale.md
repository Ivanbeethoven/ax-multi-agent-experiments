# 正式实验规模

> 当前论文设计见 [五 RQ 方案](../../paper-design/README.md) 和 [参数清单](../../paper-design/design.json)：七份 trace 的固定工作量为56任务，正式后端为四个 RustFS 服务，另测 Packed 数据库减压和首次构建成本。下文旧64任务与旧四份 trace 规模保留为历史工具说明，不是新方案的任务表。

5个容器只用于检查部署、回放和采集。4个客户端的固定64任务组用于比较同一批工作量。大规模结论另由下面三组实验回答，外部对照仍只有JuiceFS。

## 1. 活跃工作区：4 → 128个客户端

| 客户端容器 | 每容器并发 | 总并发工作区 | 每批完整trace | 三批回放次数 |
|---:|---:|---:|---:|---:|
| 4 | 4 | 16 | 16 | 48 |
| 16 | 4 | 64 | 64 | 192 |
| 64 | 4 | 256 | 256 | 768 |
| 128 | 4 | 512 | 512 | 1,536 |

每个worker各运行一份Django、sklearn、SymPy、pytest，三批使用新工作区。共12批、2,544次回放/系统；BrewFS与JuiceFS合计5,088次。不把所有消融都乘上这张表。

每个客户端固定4 CPU/8 GiB、JuiceFS缓存1 GiB、buffer 256 MiB。四个点只增加客户端数量，后端资源和参数保持不变。准备全部完成后，协调器统一放行回放；准备耗时另报。这个模式的工作量随客户端数增加，报告正确任务/秒、回调/秒、每题完成时间和资源用量，不用批次时间直接计算固定工作量加速比。每批也报总完成时间和失败数。

```bash
python3 scenarios/k8s-containers/scripts/campaign.py \
  --profile scale --systems juicefs --out runs/k8s/juicefs-scale.json
```

计划内有每批worker_count、并发数、每项trace和目标worker，默认execution_enabled=false；这是任务表，执行仍需要接入协调器。按4、16、64、128顺序验收，禁止因一个点慢就改掉该点后端配置。

**通过条件与记录：**

- 全部回放通过操作数、读写字节和最终树校验；失败/超时保留在分母里。
- 容器CPU、内存、限流、JuiceFS FUSE请求及S3请求、Redis与RustFS资源同时收集。
- 单个回放器的JSON解析/哈希可能先耗尽客户端CPU；遇到这一情况，不能解释成存储吞吐上限。另报原生FUSE请求延迟和后端占用。
- 每档记录真实节点分布。128个容器不是128台机器；节点未知时只写容器并发规模。

## 2. 已保存状态：1千 → 10万个工作区

这组回答“多数Agent暂不运行时，保存和重新打开它们需要多少资源”。不启动10万个回放进程。

| 项目 | 固定方法 |
|---|---|
| 总工作区数N | 1,000、10,000、100,000；按N递增建库，每次测试记录实际完成数 |
| 输入 | 原F1：1 GiB、32,896个文件；所有工作区从同一个父版本创建 |
| 每个工作区私有内容 | 1 MiB修改＋64 KiB状态，按workspace_id生成不同内容 |
| 创建 | 16个worker，每个最多4个未完成创建，共64路；记录提交/确认时间 |
| 保存后 | 停止该工作区的操作进程，保留目录及状态，不卸载JuiceFS挂载 |
| 打开与继续 | 在总量N固定时，每轮选min(N,1024)个不同ID，64路并发，先读取并核验64 KiB状态，再核验指定4 MiB数据 |
| ID选择 | 从0..N-1按seed=20261024+repeat洗牌取前min(N,1024)，保存实际列表 |
| 主要指标 | 建库总时间/成功数、创建与重开p50/p95/p99、Redis内存、客户端空闲内存、对象请求和字节、保存状态总占用 |
| 校验 | 每个工作区私有写入和状态摘要；按已确认创建的ID排序，抽取首、中、末三个做完整树核验；不能声称全量目录都做了完整树哈希 |
| 停止规则 | 一档创建超过30分钟、出现OOM/写入错误，或元数据服务进程用量达到两系统同设的24 GiB有效预算的90%时停止增长；Redis另检查used_memory、双方另检查32 GiB cgroup限额；记录实际数量、时间和原因 |

JuiceFS对父目录执行 `juicefs clone --preserve SRC DST`，目标必须不存在，clone后再写自己的内容；不先全量复制。父目录与全部子目录使用同一JuiceFS卷。[1.4.2 clone实现](https://github.com/juicedata/juicefs/blob/v1.4.2/cmd/clone.go)

10万个F1目录在逻辑上涉及约32.9亿个文件。能否在固定元数据预算内管理它们，正是要测的问题；不预设双方都能做到10万。创建失败/达到资源阈值时报告“在本预算与30分钟内最多完成N个”，不写成系统绝对上限。BrewFS共享元数据与Packed的2×2消融，在1千、1万两档执行；实际未实现的开关不能标成已测。

## 3. 部分迁移：256个活跃工作区中只迁一部分

128个客户端分为64个源端、64个已就绪目标端；源端每容器4个工作区，共256个。每组迁0、16、64、128个，其余持续运行相同读写循环。使用F1与明确的轮次状态，不在任意trace位置切断未关闭的文件句柄。

每轮读取并核验4 MiB、改写1 MiB、保存64 KiB状态，关闭句柄并完成保存确认后才交接；目标核对轮次和摘要，继续下一轮。每个工作区20轮，第5轮结束触发迁移；不迁移对照在同一位置记录事件。目标映射和迁移ID在开跑前冻结。

报告：停止源写者到目标首个正确操作的暂停时间p50/p95/p99、需要搬运的字节、完成/失败数、未迁工作区的操作延迟和完成量。JuiceFS目标打开原目录；BrewFS目标打开其保存版本，复制恢复是单独消融。JuiceFS的源写者由协调器停止，旧写者重新运行能否写入单列正确性结果，不能把外部停进程算作文件系统提供的写者隔离。

该组测文件和会话状态交接；Rust回放不会恢复原进程内存，也不证明OpenCode在所有题目上都能resume。

## 4. 服务端与监控随规模准备

正式扩展组固定使用以下预算；起步5容器的资源不能直接作为128客户端组的配置。两系统分时复用同一RustFS；各自元数据服务总预算对齐。

| 角色 | 正式组资源/目录 | 需要改的参数 |
|---|---|---|
| Redis | 8 CPU / 32 GiB；持久目录200 GiB | maxmemory=24gb、noeviction；持久化策略仍按实验分组 |
| RustFS s0 | 16 CPU / 32 GiB；持久目录2 TiB | 单节点拓扑固定；记录真实卷类型/带宽 |
| monitor | 8 CPU / 16 GiB；持久目录200 GiB | 同一Prometheus/Collector/结果接收链路；固定抓取频率 |
| 每个worker | 4 CPU / 8 GiB | 输入80 GiB，缓存预算固定；目标目录按实际占用留余量 |

最大为128个worker＋3个服务容器＝131个容器。Redis的2 GiB和24 GiB配置分成两组，运行前保存CONFIG GET；不能把内存更大的配置偷偷放在某一系统。单RustFS达到上限后，结果可说明该拓扑的上限；再用4个RustFS容器重跑相同端点属于另一组，两个系统都重跑。

全部worker仍1秒采样；监控不可按task_id/workspace_id给每条I/O加标签。每个规模先做采集开/关配对；monitor的CPU、内存、写入量、抓取失败与结果传输缺口也记录。监控开销超过5%、出现持续采样缺口或结果发送落后时，修复采集后整组重跑，不删掉忙时样本。

128个客户端各存一份约4 GiB压缩输入，总下载约512 GiB；提前分发并校验，放到任务计时之外，同时单列准备流量。任务结束只传回指标/结果，不重复传trace。每个规模每系统先一批验收，确认输入与采集正确才补足三批。

## 5. 能说明什么

四种trace足以做可控的扩展性比较，覆盖面仍有限。后续应补更多独立采集任务及不同仓库大小、元数据比例、读写比例；修改副本路径或重复次数不算新增任务。当前结论限于这四种已记录文件负载，以及F1/F2固定实验。
