# 公共运行协议

## 1. 冻结与资格

执行开始时冻结官方 BrewFS 默认分支完整 SHA、JuiceFS 版本、四个 RustFS 服务版本、镜像摘要、补丁、配置与构建参数；整个配对批次不升级。现有计划指定 JuiceFS CE 1.4.2，执行前核对实际二进制。研究后端扩展单独编号。记录真实物理节点、容器配额、卷、网络、EC/副本配置、元数据持久化和故障域，不能用容器数代替节点数。

每个配置提交能力记录：基础读写、稳定版本、带修改父状态 fork、重开、源记录安全退休、跨 worker 写权转移、故障接管、后端布局、生效指标。每项是 `qualified/unsupported/not_checked`，附独立读回证据。三组作者名称、库函数存在和通过普通读写均不代替这些验收。

## 2. 共用环境

主组4个客户端，每个4 CPU、8 GiB和1 GiB文件缓存；元数据8 CPU/32 GiB，实际有效内存预算24 GiB；四个对象服务各16 CPU/32 GiB；监控8 CPU/16 GiB。迁移另有4个已就绪目标。这些是计划配额，资源不足时先签出独立的小规模资格组，不用缩小后的数据填主组。

两系统分时复用相同资源；桶、元数据空间与运行ID独立。缓存总量包含文件缓存、元数据缓存和进程内缓存；页缓存由相同cgroup上限约束并单独观测。后端缓存通常无法严格清空，统一准备顺序、记录状态、轮换系统顺序，不宣称后端冷。

固定实际对象粒度、压缩、内联、预读、获取策略、并发上传、持久化确认和校验语义。不能为获得某配置偷偷换另一条上层I/O路径。无法控制的差异登记为联合处理，不能单独归因于 Pack。

## 3. 状态、输入及操作合同

F1、F2、M 的内容与路径由 `fixtures.json` 定义，生成后再填实际摘要。所有修改表、查询表、目标表、版本树与种子在批次开始前落盘并散列。标签包含 campaign、pair、repeat、workspace、round；两配置同一逻辑标签生成相同字节。

`confirm_current` 是当前文件状态可在另一个客户端恢复的远端确认；`retain_version` 额外保证后续修改不改变该历史版本；`fork` 创建隔离可写子状态；`reopen_current` 重新访问原确认状态。不要用保存历史代替每次普通保存，也不要用复制文件树代替会话恢复。

基础 `native` 没有 fork 接口时，内部物化对照只物化必要元数据、保持同等数据共享；如果做不到，应报不可用，并可另外提供“完整复制”实际基线，不能把它当作纯 Overlay 消融。

## 4. 批次状态机与时钟

每批：分配全新运行空间 → 准备输入并验收 → 建立声明的缓存初态 → 采集基线快照 → 全体ready → 协调器发令 → 运行 → 远端排空 → 独立验收 → 保留/回收观察 → 导出原始证据。

协调器记录 `submit/ready/start/finish/deadline` 单调时间；worker本地阶段用各自单调时钟。跨worker不能相减monotonic值。端到端时延用协调器发请求到收到可信完成证据的时间，包含通信；内部精细阶段是worker局部时长，不强行拼成全局关键路径。预先报告协调消息的空操作开销。

冷客户端重建受测客户端进程/缓存命名空间；准备和完整树验收结束后再重建冷初态。只热索引时仅预取索引，热元数据时重放相同查询后重置计数；payload温度另记。不清空共享宿主全局缓存来干扰其他任务。

## 5. 重复、顺序和截止

每参数格是一个comparison block，所有配置按固定种子20261026随机排列，每格3个独立重复；每次重复重建初态。规模按worker数递增，格内顺序随机。原始pair与顺序保留；同一批内的K前缀、子分支、请求和版本不是独立样本。

截止时停止新发令、记录在途请求，并按对应协议观察排空；不得无限重试。失败由分配表保留：功能不支持、语义失败、超时、资源拒绝、采集失败、基础设施失败分别记录。修复后是新运行，原失败不删除。三个初始重复只报原值、中位数和范围；推断性结论须依据独立pilot冻结样本量。

## 6. 实验层级

- smoke：验证真实操作、采集和内容断言；不用于排名。
- core：固定的主比较，预算覆盖整个comparison block后才启动。
- extension：低复用、低局部性、高修改、极深/高并发等边界；预先规定，不按有利结果选择。
- conditional：依赖额外实现、指标或真实Agent接口；未验收不转成“零开销”。

不能将所有文件内的参数做笛卡尔积。`execution-grid.json` 每个group给出一个明确的小矩阵；既有组作为对照复用时须满足同一资源、初态、版本、顺序和计时合同，否则补跑。

## 7. 保存材料与恢复能力

每run保存：frozen config、输入摘要、命令与返回码、事件日志、资源/服务原值、阶段结果、内容断言、对象与版本清单、回收观察、失败原因。高频采集不扫描全树；完整验收与性能读取分开计时。元数据和四个对象服务的采集必须覆盖构建及排空尾部。

现有工具可下载/校验、生成确定性输入、单任务回放/终检、采集资源、导出结果。分布式屏障、机制操作、按层计数和真实会话接口需要验收或补齐。文档中的动作名是操作合同，未绑定到真实CLI前不能直接执行。

# 01 能力、语义与计量验收

对应 `qualification`；为全部 RQ 提供入口证据，不提供性能结论。组 `q_smoke` 对 native、native-overlay、native-overlay-pack、JuiceFS 各执行一次完整验收；不适用的能力逐项记录，不使整个配置自动通过或失败。

## 准备

冻结版本、配置、节点身份、预算和指标清单。用 F1 的前256个小文件、两个4 MiB文件作为 smoke 子集，单独记录子集摘要，不能称其为完整F1。元数据和对象端使用全新运行空间。生成100个存在/100个不存在查询、128个4 KiB写入和8个删除/改名动作，冻结操作顺序。

## 操作及断言

1. 基础路径：创建、读取、覆盖、截断、rename、unlink、sync；另一客户端核对类型、长度、模式和内容，确认回调成功不是唯一证据。
2. 版本：修改父目录和数据后确认P，再改当前父状态；P应保持原内容。记录取得一致版本的实际步骤、暂停及元数据/对象工作。
3. 分支：从P创建两个可写子状态；各写不同内容，父和兄弟必须不变。核对继承的是修改后的P。native通过物化适配器时登记额外工作；若适配器复制全部payload，标为不同控制。
4. Packed：记录构建输入、索引/页面/manifest摘要、上传与验证完成、发布身份；独立客户端读取Packed下层。记录lower类型和upper路径，确保配置名称确实改变表示。
5. 重开：关闭工作进程，在另一个worker打开指定确认版本，核对状态；记录是否复用了同一PVC。不能把同PVC重启写成任意节点迁移。
6. 写者：明确提供的是进程停止、协调器提交拒绝还是存储端拒绝；尝试旧身份写入并独立读回。具体故障场景留给08协议。
7. 指标：用已知100次查询/128次写入检查逻辑计数；DB、对象和系统调用计数可以不同，但必须解释聚合范围。对象长度及实际B/q从持久状态核对。

## 工具可用性

- `scenarios/k8s-containers/scripts/run_case.py` 已实现单任务 prepare/replay/verify，总期限覆盖三阶段，可对一份完整Pytest继续做资格检查。
- `campaign.py` 仍只生成旧四份trace计划；不得把它的输出改名为本轮七份主组。
- `baseline-operation-contracts.json` 保留旧B0–B4映射与接口缺口，可参考动作语义，不能用旧 `open`（可能clone）代替本轮 `reopen_current`。
- 为每项新动作记录适配器、函数/CLI版本、参数、返回证据；未知命令留空。资格文件不能仅填布尔值。

## 计量质量与停止

构建、发令、首个正确读、远端确认、独立验收、排空分别记事件。1秒资源/客户端采样、5秒元数据采样；保存四个对象服务的实际指标定义。先做采集开/关配对，采集开销超过5%时降低频率后对所有配置统一重测，不能仅关闭慢配置的采集。

内容、隔离或确认契约不满足：阻止对应机制实验；不存在源退休能力：只保留源版本而继续读性能实验；没有物理I/O指标：允许HTTP层结论，禁止推断磁盘节省。没有真实会话接口：文件实验可继续，Agent验证保持未执行。

输出 `capabilities.json`、`operation-bindings.json`、输入/对象/版本清单、独立断言、原始指标与命令。每条能力带revision、configuration、contract、observed evidence和限制；能力表用于分组准入，不是论文结果表。

# 02 Overlay 的开销、fork 与分支形状

对应 `overlay_fork` / RQ1。先证明不使用Pack时Overlay的贡献，再把Pack交给04/05协议。假设：引用父状态能少做元数据物化，但层解析、写入及版本固定本身可能增加开销。

## A. 日常开销：`o_ops`

配置为native、native-overlay、native-overlay-pack、JuiceFS；并发1/16，每格3批。F1内容相同，Pack构建在准备阶段单列账单；本组只报告准备后访问。固定payload、对象大小、缓存总预算和持久化语义。若Packed路径强制不同payload格式，应标为联合处理，并另找可控制的metadata路径。

每批串行执行五个子场景，每个子场景重建源状态和冷客户端：32,768次存在查名、32,768次属性读取、固定256 MiB的4 KiB读取、256 MiB的4 KiB覆盖写、256次“写4 KiB＋sync”。总操作表固定，不随并发增加；round-robin分给执行槽。写入/sync产生的远端债务计入尾部，不用回调返回代替确认。按场景分别报耗时，不能将它们当五个独立批次。

主要输出：逻辑操作延迟分布、批次时间、DB请求、对象请求、CPU、写确认及排空。此组揭示Overlay与Packed在不fork时可能支付的额外代价。

每个子场景测量期限900秒、尾部300秒、单请求期限10秒；五个子场景的阶段预算总计6000秒。超时请求保留，不能无限补做直到凑够成功操作数。

## B. 带修改父状态的fork：`o_fanout`

native（合格物化适配器）、native-overlay、JuiceFS三组；子数1/16/64，每格3批。F1父状态先改1 MiB、删除32个小文件、改名另外32个小文件、写64 KiB轮次状态，再取得确认版本P。删除/改名集合来自固定排列，不得与读验证集合冲突而不更新oracle。

记录 `parent_modify_start → parent_confirmed`。所有fork请求在共同t0进入队列，最多16个并发创建；各子独立挂载/打开后先读取并校验P的改动，再写自己的1 MiB和64 KiB状态并确认。数据块按子ID确定；每个子有独立namespace，物理内容标签不同，以识别实际新增字节。

分别报告 `t0→child_ready`、`t0→first_correct_read`、首个持久修改、保存确认，以及全批完成；队列包含在fork端到端时间。固定P的准备成本既单列，又计入完整fork批次账单。每子截止600秒，全批1200秒，最多300秒排空；失败/未就绪保留，不仅统计成功者p95。

断言：每个子继承P而不是干净F1；写子后P和其他子不变；独立客户端按版本重开；检查目录项、内容、权限与状态摘要。不能仅检查子路径是否创建成功。

## C. 固定状态数与深度：`o_shapes`

同三配置，星形、四叉树、四条深8链，共33状态/32条fork边，各3批。父索引依总体方案；每边写1 MiB，全部状态保留。按拓扑层启动，层内最多16并发；逐边记录ready/save，另报树完成时间。不同树关键路径不同，不将树总时间直接解释成单次lookup变慢；补充对叶节点的同一固定读查询，观察解析深度影响。

递归oracle按父版本和边修改计算每节点内容，物化对照使用相同对象共享语义。全树构建截止1800秒，尾部300秒。用元数据记录/字节和引用数解释曲线，不能用总目录数代替私有元数据。

叶访问固定取4个叶节点，每叶4,096个lookup＋4 KiB校验读，使用相同逻辑查询表，单独900秒截止。星形、四叉树和深链的叶数不同，不能将“读全部叶”当作等量负载；记录这4个叶实际深度和选择种子。

## 扩展与解释

`o_large_delta`：子数16，写入128/512 MiB；`o_fanout256`：256子、每子1 MiB。仍固定16个创建槽，防止增加机器/并发制造收益。修改量超过小增量区域时收益消失，是机制边界。记录实际CoW与对象复用，native复制全部payload的结果另列，不算纯Overlay收益。

图：扇出→首次可用/全批时间；同图另列父确认；深度→叶读取延迟和元数据；子修改量→新增物理/逻辑字节。native-overlay等于或劣于物化对照、层深导致持续放大，均削弱相应主张。

# 03 历史保留、可恢复容量与回收

对应 `retention` / RQ1、RQ5。测量可恢复状态数与成本，不把仅存在一条控制记录称为可恢复工作区。

## 矩阵

`r_core`：native（合格物化适配器）、native-overlay、JuiceFS；目标状态1,000/10,000；每格3批。`r_limit`扩展到100,000。此组不默认打包；Packed源记录和包的生命周期由05协议单独测。

同一个固定F1父版本产生N个兄弟历史状态，每个私有1 MiB改动和64 KiB状态。用各不相同的内容标签避免去重差异；共享父数据只计一次。若需“深历史”，另用02协议的形状控制，不能与N兄弟数量混在同一曲线。

## 流程和停止条件

1. 准备并确认父版本，记录父构建成本、源状态大小与后台任务。
2. 64路创建、修改和确认；每完成一个记录真实远端版本ID，随后关闭执行进程，但保留历史可恢复引用。
3. 从提交第一项起最多1800秒；达到目标N、观察到OOM、确认/隔离错误，或元数据使用达到实际有效预算90%时停止新提交。已有任务最多300秒收尾；继续记录达到停止条件的原因与在途结果。
4. 对成功状态按种子20261026抽最多1,024个，另固定最早和最晚状态（若未被抽中则追加并说明数量）。另一个worker重开，核对64 KiB状态、所有修改块及4 MiB不变区域；报告采样覆盖，不声称全量内容都验过。
5. 删除成功状态中按ID奇偶选出的约一半引用，记录删除接受与实际引用变化；保留600秒保护期，观察3600秒。保留状态在开始、中途、结束各读回同一采样集合。

不能以删除文件数推断GC成功。记录数据库行/存储文件大小、逻辑live对象、保留对象、垃圾候选、已删除对象及实际对象端占用；数据库压缩或RustFS扫描未完成时保留残留。删除引用后的可达性验证优先于测量释放字节。

## 指标与前台干扰

从第一次创建到收尾的正确确认数、创建/保存/重开p50和p95、资源拒绝、内存峰值、源/共享/私有字节及驻留byte-seconds。容量定义为“在给定预算和截止下的正确完成数”，不是系统绝对极限。目标N未达到时仍保存曲线及失败分母。

回收期维持一个独立已存在的探针工作区，每秒1轮：校验4 KiB、覆盖另4 KiB、确认；截止2秒，最多1个在途，忙时将本轮记为miss而不补发。保存600秒删除前基线及3600秒观察期，报按时完成率与延迟；它是固定干扰探针，不是饱和吞吐测试。

新引用产生后旧状态不可读、删半后保留状态损坏，立即标语义失败。若重开能力不支持，则不能称本组为“可恢复容量”，只允许降格为元数据保留开销并明确区别。

图：正确状态数→元数据/对象占用；时间→释放量与保留未释放量；重开延迟与探针完成率。保留成本增长接近物化、回收长期落后或元数据库内存先耗尽均是必须解释的边界。

# 04 Packed 的访问路径、数据库减压与前台干扰

对应 `packed_access` / RQ2。主对照是native-overlay与native-overlay-pack，使用同一一致固定版本、相同upper、payload位置和对象布局。不能以可变数据库对比可永久缓存的固定包后把全部差异归给分组组织。

## A. 访问路径：`p_access`

M规模N=32,768/1,048,576，每文件1 KiB、每目录256文件。16消费者；两种初态：cold-client、metadata-warm；六种查询各成一格；每格3批。主组消费者读取相同逻辑查询表，纯元数据比较关闭内联与压缩，建包时间在本组准备账单单列，由05协议计算回本。

每消费者32,768个顶层查询，按固定顺序串行发出；消费者之间并行。每查询期限2秒；每批测量上限900秒、在途收尾120秒，超时保留。冷只指批次开始时缓存为空，不宣称整个会话每次都冷。所有配置同一格使用相同逻辑ID，inode号码由各配置实际映射而来。

| 查询族 | 冻结的操作与返回量 | 目的 |
|---|---|---|
| positive_random | 对存在路径按固定seed均匀有放回抽样，lookup一次 | 低名称局部性的查找 |
| negative_mixed | 与存在查询严格交替；另一半名称加不相交前缀，先断言不存在 | 缺失查询和证明成本 |
| inode_attributes | 对已经解析的逻辑inode读取属性；解析成本准备时单列 | 分离属性访问；若只能POSIX按路径stat则另名报告 |
| neighbor_names | 随机选目录，连续读取32个相邻名称，然后换目录 | 联合页面与局部性 |
| readdir_attributes | 一次完整目录枚举，再对返回的256个条目读取属性 | 每顶层操作的256个结果不能伪装成一个等量lookup |
| lookup_read | lookup后读该文件1 KiB并校验 | 元数据优势能否传导到文件读取 |

目录、名称及查询文件散列冻结；重复次数不会增加任务种类。纯属性微基准与POSIX工具路径分开报告。lookup_read主组payload初态统一为客户端冷，metadata-warm仅热元数据。若实现无法独立控制，改名为实际复合缓存状态并列出限制。

`p_access_sensitivity`只扩展N=1,048,576下的positive_random/neighbor_names、消费者1/64、shared/disjoint和cold-client，不再乘全部查询。disjoint按消费者划分目录池，但每人工作量仍为32,768次；报告总体工作集随消费者增加。

`p_index`扩展只热索引的初态：N=1,048,576、16消费者、positive_random/neighbor_names、每格3批，与相同参数的cold-client和metadata-warm主组对照。预取仅涉及索引，须用计数证明没有提前取联合元数据或payload；原生对照只热等价路由结构。若不能构造等价的索引热/记录冷状态，记unsupported，不能拿两种不同预热量比较。

## B. 对中心数据库及可写工作区的影响：`p_probe`

两规模、两表示、背景到达率0/r/4r，每格3批。探针在**同一元数据服务、独立可写工作区**，80%属性读、20%覆盖4 KiB后sync；该探针不访问被打包lower。固定轮换一组32,768个探针文件，操作表在测量前生成。

先对两配置无背景条件分别用5分钟窗口测可持续探针吞吐：队列不持续增长、按2秒期限完成比例≥99%。递增速率的pilot只用于标定，取两者较低可持续值r并冻结。主探针到达率为0.25r；背景针对固定lower发positive_random，按同一预生成时间表0/r/4r到达，最多64个在途。

1分钟预热、5分钟计量、最多2分钟排空。负载发生器按计划到达时间记账；队列满仍记录应到达请求，截止前未发出记admission/deadline miss，不用“等前一条返回再发下一条”掩盖饱和。报告计划/实际发令时间差；发生器本身饱和的格不得解释成存储极限。2秒期限从计划到达算起，另报服务开始到返回的处理时间。

输出探针按时完成率、队列和p50/p95，背景发出/完成/超时数，DB命令、CPU、内存、持久字节、AOF重写等后台活动，客户端及四个对象服务的CPU/网络/请求。必须同时看到“中心少做了什么”和“其他地方多做了什么”。

## C. 请求归因和额外对照

每次逻辑操作区分lower DB、upper DB、控制DB、索引页、联合元数据页、数据定位描述符、payload。Redis聚合命令数只能说明总量；若无法分层，应补受控单类流量或计数器，不能直接宣称lower减少了某个精确比例。

`p_readonly`为条件组：同一个固定版本的native只读与Packed只读，在不创建私有upper时运行positive_random和neighbor_names、16消费者、两缓存初态。需要资格验证匹配读语义和缓存预算；独立只读入口无同等控制时不排名。

`p_defaults`为扩展实际配置：N=1,048,576，lookup_read/readdir_attributes、16消费者，使用各自声明的默认内联和压缩。它报告可部署配置表现，不作为纯Pack分组归因。要完全拆开“移出数据库”和“联合分组”，还需要保持对象存放、索引、认证和预算的逐记录表示对照；未实现时明确不能完成这个分解。

图1：每逻辑操作的DB/对象请求与字节，按查询族分面；图2：背景到达率→探针按时完成率/p95，并列DB与对象CPU；图3：局部性/缓存状态→相对代价。源记录主组全部保留，数据库空间只报告实际值，不预设减少。

# 05 Packed 首次 fork、复用与版本更新成本

对应 `packed_lifecycle` / RQ2、RQ4。对照native-overlay与native-overlay-pack；强调Pack是可选择的固定版本表示，不是fork的前提。access主组回答请求路径，本组回答为了获得该路径需要先付出什么。

## A. 从相同源状态到第一个可用子分支：`p_first`

M规模32,768/1,048,576，各配置3批。源状态是相同内容、尚未准备供本实验复用的可写父状态。先准备数据并确认基本持久性；初始文件导入成本单列但两配置一致。共同t0发“建立可fork的版本并创建一个子工作区”，从这里计入一致性截断、原生版本固定及Pack所需工作。

记录：停止/限制并发写入开始与结束、一致版本可用、扫描/构建、对象上传、校验、版本发布、子状态建立、目标首个正确查名/1 KiB读取、子首个持久修改。阶段允许流水化；总时间直接测t0到结果，不能相加重叠阶段。native也承担实际seal和绑定成本，不给它一个人工零准备起点。

从第一阶段起计数据库操作、CPU、读取/上传字节、临时磁盘峰值、对象和数据库驻留量。主组源停止新应用写，避免同时比较不同一致性协议；写入持续更新条件由C组明确处理。

首子总期限1800秒、尾部300秒；阶段失败要保留此前已产生的临时对象、耗时和可恢复性。验证父固定版本、子读到的身份及子写隔离；不得先全树预热目标再记录首读。

## B. 固定版本反复使用：`p_reuse`

两规模、两配置，各3批；每批从未为本批发布的源开始，包含A组相同准备成本，然后依次运行256个子消费会话。每会话fork一个子工作区，读取32,768次固定查询（positive_random与neighbor_names各一半、固定交替），写64 KiB私有状态并确认，结束后保留子版本到观察末端。会话一个接一个执行，保证每个K前缀有明确完整工作量；并发消费的作用由04协议单列。

在K=1/4/16/64/256前缀采样累计账单、实际经过时间和当前占用；这些前缀来自同一批，不是五个独立重复。每个子使用新客户端/独立缓存预算；共享宿主、后端和公共页缓存仍可能变暖，记录其状态。metadata-warm收益由04协议测，不能把256子复用写成256个独立冷后端。

每会话期限120秒，完整256会话上限32,820秒（1800秒准备＋256×120秒＋300秒尾部）；失败会话计入分配分母。若某K前缀包含失败，只报告真实完成数/成本，不能当作完成K次的回本点。采集前缀时的屏障开销也记录。

## C. 连续发布与变化频率：`p_update`

N=1,048,576；每版本K=4/64；每次修改0.1%/1%/10%文件；两配置各3批，每批8个版本周期，末次使用后保留0秒（仍服从实际安全回收条件）。K是每次更新之间的实际消费数量，不能只换一个版本号。每个版本的消费查询/写入和缓存政策沿B组。

按seed排列选择floor(N×比例)个文件（至少1个），每次改变内容并交替改变模式位；变更表和内容版本标签冻结。修改发生在上一周期结束后，应用写入暂停期间固定下一版本。记录实际全扫描、增量扫描、重用页、重建页、索引、上传、验证和发布，不能假定实现有增量packer。

每次发布后保留一个旧版本读者，在新旧各抽1,024条已修改记录读取并校验版本，随后释放该短期读者；这个固定短期pin的额外驻留计入账单。非必须旧引用按策略释放。每周期准备≤1800秒，每会话≤120秒，回收观察≤3600秒；整批截止由这些固定预算求和并在运行清单冻结。

扩展 `p_keep`：变化1%、K=64，末次使用后保留600秒，观察历史持有成本；其它条件保持一致。更新间隔不是任意外推的秒数：先报告实测每周期时间和消费频率，再画频率边界。

## D. 源记录退休：`p_retire`（条件组）

仅native-overlay-pack，N=1,048,576、K=64；保留源记录与按实现生命周期协议安全退休两种政策，各3批。不能直接删数据库key模拟退休。验收旧引用、读者pin、并发源访问和回收安全条件，明确哪些记录必须保留。

报告源记录逻辑量、DB实际驻留、压缩/重写尾部、对象新增量和读取正确性。若当前实现不能安全退休，组记unsupported；查询减压结论不依赖退休成立，也不能因此声称数据库存储下降。

## 成本与结论

对每个资源c计算 `ΔC_c(K,T)=C_packed,c−C_native,c`，共享准备计一次，驻留按实际存活区间积分，失败工作也计成本。单位分别保留，金额只有价格与时间基准齐全才算。逐K/变化比例报告原值和差值，不假设单调，不把首次负值外推到所有更大K。

图：首次fork关键阶段；K→累计资源差值/首个可用时间；变化比例×复用次数→观察到的优劣区域；源保留/退休→DB与对象驻留。少复用、频繁重打包、冷对象读、临时构建峰值大或原生缓存已足够，都是可能让native-overlay更好的条件。

# 06 对象粒度、后端布局与获取策略

对应 `object_granularity` / RQ3。保持Overlay/Pack状态不变，按“对象形成、布局、获取”三步控制变量；不把启用某标签等同实际处理变化。

## A. 客户端对象形成：`g_client`

基础native路径、F2、g候选1/4/8/16 MiB；三个子负载各一格，每格3批。后端布局、冗余率、压缩、缓存、预读、校验、并发度固定；只运行真实支持的g，遇不兼容不能偷偷改变chunk几何。每格先用完全相同逻辑写顺序生成F2，再确认远端，保存对象长度分布与映射；不同g形成不同对象集合是本组处理本身。

- sparse_read：16消费者，每人1,024个4 KiB记录，固定有放回采样key；另记各消费者重叠，查询表相同于全部g。
- scan：16消费者各扫F2中不重叠的4个完整分片，总体1 GiB，校验内容；不让每人扫1 GiB从而改变总工作量。
- overwrite：16消费者在互不重叠key池各覆盖1,024个4 KiB记录，总64 MiB逻辑修改，然后远端确认。修改标签和顺序固定，报请求返回与排空总时间。

准备/上传本身计账，读测量与写测量分开。冷客户端初态；每格900秒测量、最多300秒排空。独立最终读回所有修改记录和固定不变样本。小对象可能降低局部读写放大但增加对象请求/索引/元数据，这是需要同时观测的效果。

## B. 固定对象后的获取策略：`g_fetch`

保持同一g=4 MiB对象集合，比较实际支持的Range与整对象获取；读取类型为4 KiB对齐、4 KiB跨对象边界、1 MiB范围。16消费者各1,024请求，3批。对边界位置明确定义为对象边界前2 KiB开始、共4 KiB；如果实际认证粒度仍要求整对象，记录实际HTTP/校验而不把请求头当成功处理。

相同cache、合并、并发和预读；不控制这些条件就只能叫完整客户端策略比较。跨对象读oracle按逻辑字节串校验，不能把各range单独成功当完整文件读取正确。

## C. 后端编码和校验：`g_backend`、`g_verify`（条件组）

冻结相同对象字节、长度分布、请求列表；只改变后端合法策略。`g_backend`比较default、一个合格固定B、长度选择策略，使用A组三类负载；`g_verify`固定B和对象，只比较default q与一个合格较小q，使用对齐/跨界读取。每格3批，具体B/q值先在资格阶段依据真实格式与冗余约束冻结，未确定时这些格不可执行。

每个对象记录请求hint、准入/拒绝、最终持久B/q、对象长度和校验方式。默认与自动得到相同布局时保留为no-treatment控制，不解释成自适应收益。客户端g可配置不代表存在访问驱动的自适应g控制器。

降级读取/修复另行资格通过后再列附加组，固定故障分片数和失败节点、同一对象集合、代码率及调度资源；没有这些证据，本轮不作恢复性能结论。研究RustFS后端与官方发行版本分开记录，不将扩展结果归给所有S3服务。

## 观测与图

记录对象数/长度、GET/PUT/HEAD次数、HTTP有效字节、数据/校验分片实际读写字节、checksum/编码CPU、尾部等待、读/写正确完成、修复流量。网络/HTTP量不能代替磁盘物理读取；不可观测时填null并缩小结论。

图按链路排列：g或实际B/q → 对象/请求数 → 传输与物理工作 → CPU/尾部 → 正确工具完成时间。读取变快但写/恢复开销更大必须同图或相邻报告；顺序扫描下没有优势是边界结果。

# 07 部分工作区迁移、冷目标与邻居

对应 `migration` / RQ4。对照native-overlay、native-overlay-pack和JuiceFS；每种配置都与自身不迁移运行配对，不用不同文件系统间差值代替迁移开销。迁移是重新打开同一确认状态，不强制clone或复制整树。

## 矩阵

- `m_clean`：16工作区、4源/4目标；虚拟选中数1/4/8；action=stay/move；已确认状态、冷目标、4个迁移槽；每格3批。
- `m_dirty`：选中4个，1/16/128 MiB逻辑改动尚未确认；其余同上，stay/move配对、3批。
- `m_warm`扩展：选中8个、已确认、暖目标、迁移槽1/4，stay/move、3批。
- `m_queue`扩展：选中8个、已确认、冷目标、1个迁移槽，stay/move、3批。
- `m_scale`扩展：64源/64目标、256工作区；选中16/64/128、冷目标、4槽，stay/move、3批。物理节点部署不能由这些数量推定。

stay组保留同一虚拟选中集合以核对轨迹，但实际迁移数为0；不人为暂停stay组模拟迁移等待。选择ID用固定排序等距取样，目标为下一源组对应目标worker；两配置使用相同对应表。

## 单批工作负载和触发

每源4工作区，从同一F1独立生成；每轮读取并校验4 MiB、修改1 MiB、写64 KiB轮次状态。selected共20轮，第5轮完整工具结果后进入触发边界。clean组已确认第5轮；dirty组在上次确认后再写指定D MiB并关闭句柄但不做应用保存，记录逻辑未确认量、实际已上传量和真实缓存dirty量，不能把D一概称作驻留脏字节。

各selected到达边界的时间逐个记录。协调器在它们就绪后发共同迁移请求t0，先到达者在屏障前已经停顿的时间也必须计入“工具边界到恢复”总暂停；同时单列`t0到恢复`，不能用后者隐藏屏障等待。等待迁移槽和目标就绪均从t0起计。stay组在相同进度事件记标记后继续，不等待人工迁移屏障。

neighbors使用独立固定时间表，每5秒提交一轮，持续600秒，每轮120秒期限、最多300秒收尾；不得因系统慢而减少应到达数量。目标在实验前已分配并可用，其待机资源计入共同预算；云资源申请耗时不在本实验迁移定义中。

## 迁移动作与时点

按真实路径完成：停止新的工具动作 → 关闭句柄 → 排空并确认待保存文件 → 必要的一致版本/Pack构建和发布 → 撤销或失效旧写权 → 目标取得有效写权 → 重开原状态 → 核对轮次和预定内容 → 首个正确读/写 → 完成剩余轮次。

已确认组仍单列此前确认/打包成本。Pack不能变成所有迁移的前提；native路径独立执行。JuiceFS在目标重开原目录和已远端确认数据，不能额外clone来制造迁移成本。应用session.bin仅是64 KiB文件状态，实际会话恢复由11协议验证。

目标首个正确操作截止t0+600秒；selected续跑截止t0+900秒。若初始工具边界等待更长，另报包含该等待的完整暂停。结束后独立确认最终轮次20、文件摘要、源/兄弟隔离；失败不得只保留成功迁移的p95。

## 缓存、测量及图

冷目标在准备验收后重建缓存，禁止性能计时前完整树扫读。暖组先在该目标读取固定清单，预热成本单列；随后重复使用相同初态。邻居、源、目标、元数据和对象资源一起记录，避免把资源转移称为减少。

端到端时间由协调器请求和证据回执计算；本地drain/pack/open细分不能跨时钟相减。图：selected数量→完整暂停/队列/首读；dirty量→发布及暂停；邻居完成率/p95相对stay；源/目标/服务CPU和字节。慢冷读、打包预付款、旧写者未真正停止或邻居显著下降，分别限制对应结论。

# 08 发布、迁移与旧写者的故障验证

对应 `recovery` / RQ4。`f_fault`包含native-overlay、native-overlay-pack、JuiceFS，四个故障位置，每格20次，合计240个计划尝试。它是正确性活动，不是240个性能重复；不支持相应保证的配置保留为unsupported，不能用终止进程冒充存储fencing。

## 输入、权威与故障点

完整F1父状态，记录已确认版本V0和内容摘要；工作进程产生1 MiB新内容及64 KiB状态V1。每次从新运行空间和V0开始。协调器在外部持久记录“已确认”的权威证据；客户端自己说写返回不能等同远端版本已确认。

| 故障点 | 触发位置 | 必须观察的结果 |
|---|---|---|
| before_confirmation | 部分新数据/元数据工作已经发生，确认/发布尚未完成 | V0仍可恢复；V1可完整成功或完整不承诺，不能出现混合已确认状态 |
| after_confirmation | 外部已保存V1的确认回执，源尚未正常退出 | V1全部可恢复，不能回退到V0冒充成功 |
| source_coordination_loss_storage_alive | 源失去协调连接，但确实仍能到达DB/对象服务；目标开始接管 | 实际旧身份写/发布尝试的接受或拒绝，以及独立读回结果 |
| target_recovery_failure | 目标已取得某阶段恢复权威、尚未给出首个正确操作 | 第三客户端重试恢复，权威和状态一致，无双写者或重复公开版本 |

每次记录故障hook到达证据与成功注入证据。时机未击中单独记`injection_missed`，不称测试通过，不无上限重试；20是计划尝试数，另报实际击中数。没有可验证hook/网络隔离能力的点保持未执行。

## 步骤

1. 独立观察者保存V0、源身份、写者generation/lease（若系统有）、预期V1和确认回执链。
2. 源执行变更并到达故障点，注入指定故障。记录是否只有进程失败、只有协调不可达或storage也断开，后者不符合第三点。
3. 目标/第三客户端按真实恢复协议打开；每尝试首个正确操作期限600秒，完整内容验收900秒。记录重试、退避和遗留状态。
4. source_coordination点用旧身份尝试固定4 KiB覆盖和版本发布，记录API响应；另一个客户端读取内容和版本。不能只检查“协调器不再派任务”。
5. 核对父、兄弟、确认内容、轮次、引用和对象清单。失败恢复后的孤儿/临时对象继续观察3600秒，不立即手工删除掩盖泄漏。

## 结论边界

无确认的新状态允许丢失并不表示事务混合可接受；任何被报告为完整确认的状态都须满足内容契约。实际崩溃前有部分写落盘时保留现象，不人为要求所有未确认字节回滚，除非系统明确承诺该语义。

分别报告进程停止、应用提交保护、元数据服务拒绝、对象层条件写的保护范围。JuiceFS若没有独占工作区写者租约，这项保证记为不提供；可另测应用协调器保护，但不把该结果当作文件系统fencing。

产物：每尝试时间线、确认日志、注入记录、旧写返回值、独立内容断言、恢复身份、孤儿清单。图以故障点×结果分类和恢复阶段分布为主，不用单个“成功率100%”隐藏未注入、未支持和不同契约。

# 09 七份完整trace的固定工作量

对应 `replay` / RQ5。保持任务总量，比较存储配置能否让相同输入更早正确完成；不是重新调用模型或重新采集。

## 矩阵与任务表

`replay_core`：native、native-overlay、native-overlay-pack、JuiceFS；并发1/4/16，4个worker，各3批，共36批、2,016项回放。native-overlay与JuiceFS的外部比较子集仍为18批/1,008项，另外18批补齐native和Pack消融；不要将后者说成额外外部系统。

每批56项：七份trace各8份。case顺序来自 `design.json.inputs.case_order`，任务i取case[i%7]，worker为`(floor(i/7)+repeat-1)%4`。在固定worker队列中按task_id顺序取任务，总活跃槽不超过C、每worker不超过4；工作分配表与调度规则在运行前冻结。不能为了缩短Django尾部动态把重任务换到另一配置没有的资源。

并发1只有一个活跃槽，但仍登记四worker分配及空闲资源；全部任务的准备、回放和终检都占用这个槽，因此C表示完整case流水的并发。并发16每worker最多4槽，保持总客户端预算32 GiB和4 GiB文件缓存，不能每个任务另分1 GiB缓存。

## 时间和状态

先下载、校验、解包七份原始archive到被测文件系统之外；准备输入归档不计文件系统运行。每项任务在被测挂载中建立初态、回放、终检；这些阶段均计入**任务服务预算1800秒**。现有 `run_case.py --timeout` 就是这个合同，不是只给replay 1800秒。

协调器另计从全批提交到分配槽的排队时间；全部并发使用同一观察截止101,100秒（56×1800+300），禁止高并发用更短窗口。任务成功须三个阶段全部返回成功并通过真实最终树验收；失败占assigned分母，不能把退出码收集完等同全部正确完成。

三种BrewFS配置都应创建同等内容与可写状态。若利用共享父版本准备，记录一次父构建和每任务的fork/初始化；如果现有prepare总是复制初态，应先报告“复制准备下的执行路径比较”，直到支持共享准备后再声明fork收益。不要临时替换部分配置的prepare而不改同一合同。

完整时间分为初始共享准备、case准备、回放、终检、远端尾部。报告整批提交到有效最终结果；可另报replay阶段，但不能据此声称完整任务同幅加速。客户端验证/哈希开销和CPU限制一起报告。

## 正确性与输出

每个case核对原始归档SHA256、初态、callback数、返回语义、实际读写内容、最终树；trace的逻辑顺序不重排。两个Pytest是同一题的两次采集，仍逐case报告但不算两个任务类别。

结果表来自冻结分配表左连接回执，缺回执记missing；保存每次失败时间和原因。同一trace的8份拷贝不构成8个独立任务种类。批内任务/请求只用于分布，独立重复是整批。

图：时间→累计正确完成数；C→全成功makespan或截止完成比例；逐case标准化时长；CPU/DB/对象与尾部资源。全失败不画“很短makespan”；没有全部成功时不外推完成时间。回放CPU先饱和时说明存储效果受回放器限制。

无模型smoke先用完整 `pytest-20261026` 的一份输入对配置做验证，再扩大；不能因为某case速度不利而从七份列表移除。功能不支持的case保留状态和原因。

# 10 固定后端下的客户端扩展

对应 `scale` / RQ5。增加客户端及工作量、保持后端资源固定；用于吞吐和容量，不用批次时间冒充固定工作量speedup。

## 矩阵

`scale_core`：native-overlay、JuiceFS，W=4/16，每格3批；每worker四个case槽、七份trace各一次。12批，共840项回放。

`scale_large`：相同两配置，W=64/128，每格3批；12批，共8,064项。主组与扩展全部执行共24批/8,904项，仍与上层总体方案一致。

`scale_ablation`条件组：W=16，native、native-overlay和native-overlay-pack各3批，共9批/1,008项；使用新的三配置配对块，避免静默复用不同时段的native-overlay结果。不把未执行Pack规模曲线外推为已测。

## 分配与时间

每worker七项，case顺序按worker和repeat循环移位，避免所有worker同时先跑Django；两配置使用相同移位表。每worker最多4槽，总4W槽。保持每worker4 CPU/8 GiB/1 GiB文件缓存，服务端与监控预算固定。任务服务预算1800秒覆盖prepare/replay/verify。

每worker7任务/4槽在无准备外债时最多两轮case预算；本组统一批次截止3,900秒（2×1800+300），从共同start算起。若准备另有共享构建，必须在该时点前单列并保留完整生命周期账单，不能将它重复加到每worker也不能隐藏。超时、槽阻塞和基础设施拒绝均保留。

必须先所有worker ready，再发共同start；ready阶段超时1800秒就记录分配/准备失败，不只启动部分worker仍标称W。四个RustFS和元数据资源不随W扩大。实际物理节点、共享网卡、服务共置及CPU限流每档记录；资源不足的档位记未执行。

## 采集与停止

统一事件、完整校验、每worker资源和四对象服务/DB计数；日志发送与回放同cgroup时标明共同开销。固定采集频率，不在大规模关闭慢配置的验证。TSDB与结果接收器若成为瓶颈，标基础设施限制并另行修复后重跑整个配对格。

任一语义破坏立即停止增长；OOM或大面积deadline miss保留本档结果，并停止更大档的自动启动。停止规则提前冻结，不能为了得到拐点后又换更大DB预算。资源扩展实验可另立新预算曲线，但不能接在原曲线上。

## 分析

报告正确任务/秒、按截止正确完成比例、逐case延迟及相对W=4的变化、DB/对象/worker CPU和内存、按时发令率、队列与限流。七种case先分别分析，再汇总固定权重；Django的操作量大不能掩盖其余负载。

图：W→正确吞吐与失败比例；W→服务资源与排队；W→各case延迟。客户端总资源随W增长，后端不增长；本组结论应明确这个资源模型。峰值任务数不能直接称为可保留历史工作区数，后者见03协议。

# 11 真实 Agent 的fork、迁移与续接

对应 `agent_validation` / RQ4、RQ5。条件组，当前仅规划。文件trace回放或session.bin读回不等同真实Agent继续运行；只有实际会话接口验收后才运行本组。

## 输入与矩阵

沿用冻结任务 `pytest-dev__pytest-10051` 和 `sympy__sympy-11618`。`a_session`配置为native-overlay、JuiceFS；条件continue/fork4/migrate，各题各配置各条件3次，共36个父任务运行。fork条件的12个父任务额外派生48个子会话，它们共享各自父任务的剩余总预算，不另算48个完整独立任务。

`a_pack`额外以native-overlay与native-overlay-pack组成新配对块，同两题/三条件/3次，共36个父任务、48个fork子会话。必须与相同任务、模型、预算和初态配对；不静默复用不同日期或模型路由下的旧基线。

执行前冻结模型完整标识/提供商路由、提示摘要、工具权限、运行环境、任务代码SHA、镜像digest、总token/金额上限、随机种子可用性及评分程序。输入文件中可能包含评分字段；给Agent的上下文只含授权题目、仓库和工具说明，FAIL_TO_PASS、参考补丁和评分材料只留评分端。

## 触发和三种条件

从原题开始运行，在第3个完整工具结果落入会话历史后触发。若任务提前完成或预算先耗尽，记未触发及真实结果，不换题补成触发成功。触发条件以完整tool result为准，不能在流式输出或尚有写句柄时切断后称安全边界。

- continue：保留同一会话和工作区继续运行，记录标记事件；没有额外fork/迁移操作。
- fork4：保存父文件/会话状态，派生4个子会话，继承完整历史、工具结果和环境。子继续提示固定且一致，若支持可重复种子则预先指定4个种子。工作区私有修改与父/兄弟隔离，原父不继续消耗预算。
- migrate：在源完成保存和写权交接，目标恢复同一逻辑会话身份/lineage及工作区，从下一步工具或模型动作继续，不能重新发送初始题目当作恢复。

墙钟期限从原任务启动算30分钟，不因恢复或fork重置；模型总预算扣除父已用量，fork四子等分剩余额度；未用预算不在看到结果后重新分配。冷/暖target、是否预启动runtime和模型连接均冻结。模型token与调用次数、存储开销、runtime重启开销分项记录。

## 证据与评分

保存父子会话ID与lineage、已完成工具结果摘要、保存前/后上下文摘要、工作区版本ID、首个真实续接工具调用和返回、最终patch及独立评分。检查工具是否无意重复、历史是否丢失、旧工作区是否仍能修改、父与兄弟是否被污染。

fork的主要任务结果是固定总预算下至少一个子正确完成的父级指标，同时报告全部子结果、选择规则和资源成本；不能把四个子成功率与一个父成功率直接并列。评分端选择最佳子可以作为“有至少一解”oracle指标，但若部署中没有该选择器，应明确不是实际用户可自动得到的成功率。

三次重复只给描述性结果，模型波动和探索策略变化不能归因于文件系统。结合无模型机制实验解释存储是否缩短暂停，不能单凭最终解题率认定Pack有效。

## 能力缺失与输出

无原生会话fork/续接接口时本组记unsupported，其他文件状态实验继续。复制会话数据库但未产生有效后续工具结果不算成功。外部模型不可用记基础设施失败，不算存储错误，也不能删去该分配。

图：工具完成时间线和迁移/fork停顿；父级正确任务数、首次有效续接时间、重复工具调用与模型/存储费用。所有展示保留预算和期限，避免“给更多Agent更多token”制造系统收益。

# 指标、成本与分析合同

所有字段来自原始证据；缺失为null，不补零。纯配置/计划字段与实测字段分开。每个批次的denominator来自冻结分配表，而不是成功回执。

## 1. 时延与正确完成

`request_to_useful = coordinator_first_correct_receipt − coordinator_request`，包含排队和必要准备；`case_service`是单worker从prepare到verify的本地时间；`submit_to_valid`包含等待执行槽；`batch_elapsed`直接量测整批，不能加各任务时长。

fork分别报父固定版本、首个子可用、各子请求到可用、首个持久修改和全批。Pack另外拆capture/build/upload/validate/publish。迁移另外报工具边界等待、t0后排队、确认/打包、交权、目标接入和第一正确操作；重叠阶段以时间线呈现，不相加制造总时间。

延迟分布保留成功请求样本，但与assigned、on-time、timeout、rejected、incorrect、missing数并列。正确完成曲线 `N_correct(t)` 按截止前**内容验收通过**计数。全成功makespan只在全部分配任务成功时提供；若有失败则报告截止完成比例及失败分类。

## 2. DB减压与新增工作

计数分为lower DB、private upper DB、control DB和build DB；对象侧区分index、joint metadata、descriptor、payload、temporary、GC。主指标为：

- 每完成逻辑操作的DB请求与对象请求，并同时报每分配操作总请求以暴露失败/重试成本。
- DB CPU核秒、内存峰值、持久数据/AOF字节；可写探针的按时完成率、计划到返回延迟和队列。
- 对象服务与客户端CPU、HTTP读写字节、解码/校验时间、缓存占用；物理磁盘字节单独采集。

`offload_fraction = 1 − DB_lower_packed / DB_lower_native` 只在相同逻辑操作量、都正确完成且native分母非零时报告。若无法分层，只报告服务总流量变化，不冒充lower offload；native为零时比例为null，保留绝对值。对象变忙或首读变慢并不自动否定DB减压，也不支持“端到端更快”。

## 3. 成本

对可加的资源c：

`C_x,c(K,T) = C_capture + C_build + C_publish + C_consume(1..K) + C_update + C_gc`。

同一原始资源事件只归属一个阶段；共享构建计一次。若阶段并发，资源核秒/字节可按事件归属加总，wall-clock不可照此求和。更新实验各版本分别计量后在整个生命周期聚合；不把每个消费者都分摊一份完整源构建后再相加。

驻留采用 `R_x(T)=∫_0^T live_owned_bytes_x(t) dt`，单位byte-seconds；同时报告源记录、可达历史、缓存、临时对象、已逻辑删除未物理回收。共享对象按实际对象ID/存活区间并集计一次，不能把逻辑引用数乘对象长度。逻辑live bytes与含冗余的物理占用分别报。

每个c报告 `ΔC_c=C_packed,c−C_native,c`。价格、地区、币种、计费时间与实例利用率明确后才能将资源换算货币；固定租用预算和边际请求费用分列，不默认CPU核秒都按独立单价收费。不得把秒、字节、请求数直接相加。

每个K是明确完成的消费数量。曲线非单调时报告所有实测交点；某个K首次负值只叫“最早观察到的回本”，不能推出所有更大K都回本。缺失/失败前缀不能与完成K次的另一配置比较成同一服务成本。

## 4. 放大率与有效布局

`read_amp_http = HTTP_payload_read_bytes / useful_application_read_bytes`；物理放大率使用真正设备/分片读计数另算。分母为零时填null。写入同理分清逻辑修改、HTTP上传、物理写和远端排空；对象数、尾部对象比例及均值/分位数同时报告。

每个对象保存实际长度、g、B、q、编码率和准入结果。hint不是effective layout。Range请求仍整对象认证时必须反映在实际HTTP和CPU中。无法采集某级数据时将该级证据标缺失，不据上一层推断。

## 5. 统计与图表

初始每格3批：全部配对原值、中位数、范围，绘制每批点；不从百万请求生成虚假的窄置信区间。正式推断前另做方差pilot并冻结样本数、主要终点和比较族。配对单位是相同输入/资源格的独立批次，版本周期、K前缀、fork子节点都是重复测量。

固定工作量先画 `N_correct(t)`，再画全成功耗时及各case差异；规模组画正确任务/秒和失败比例，按固定case权重汇总。不要平均各worker的p95，应合并原始样本或同界直方图；内存峰值注明采样间隔和可能漏掉的瞬时尖峰。

对每个图保存生成输入CSV、字段单位、过滤规则、未执行格和原始run_id映射。图的分面/颜色配置先固定，不按速度赢家更换参考配置；不能隐藏构建、保持源记录或回收尾部。

`<campaign>/<run_id>/`：`run-record.json`、`operation-bindings.json`、`inputs.sha256`、`coordinator-events.jsonl`、`worker-events.jsonl`、`assertions.jsonl`、`service-before.prom`、`service-after.prom`、资源原值、对象/版本清单、阶段结果、stdout/stderr和`outcome.json`。汇总表以运行表左连接所有结果，包括缺失项。

# 实验重构：分别证明机制贡献，再验证多 Agent 使用效果

> 逐项细化已加入本仓库的 [执行设计入口](../README.md)、[公共协议](../README.md) 和 [具体运行矩阵](../execution-grid.json)。本次只更新 AX 实验仓库，不回写论文；详细参数、阶段合同和实际批次数以这些文件为准。下文保留总体五 RQ 与原外部比较预算，新增消融会单列额外批次。

2026-10-26。状态：规划，尚未运行本方案的性能实验。此文件与同目录 `design.json` 是本轮论文 RQ 和参数的依据；较早的四 RQ、多种外部对照和旧四份 trace 任务表不再代表本轮范围。正文对应 `sections/08-evaluation.tex`。

依据：会话“规划多 Agent 共享数据实验”（01a167df-5d27-76a1-932e-698359b39715）；执行仓库 `Ivanbeethoven/ax-multi-agent-experiments` 的 734eb9b2b5eb147e003514f57036a6c558a05407；当前论文的三项独立可选机制。AX 多 Agent 运行已具备；当前容器环境不能管理 Kubernetes 控制平面，因此主批次使用已有 trace 和直接进程协调，真实会话验证使用可运行的 Agent 环境。

## 1. 主张和五个研究问题

Overlay 解决“分支如何引用父状态并保持私有修改”；Packed Metadata 解决“已固定版本的海量小文件元数据如何减少对中心数据库的依赖”；对象粒度解决“对象请求数与实际传输、校验、写入的单位如何匹配”。三者分别有成本，不要求同时开启。

| RQ | 要回答的问题 | 核心对照 | 必须给出的结果 |
|---|---|---|---|
| RQ1 Overlay | 不使用 Packed，Overlay 能否降低带修改父状态的 fork、分支保存和历史保留成本？ | native lower 上的 overlay；同接口元数据物化；JuiceFS 原生 clone | 首次可用子分支时间、保存时间、私有元数据、实际上传和保留字节、隔离正确性 |

外部对照目前只选 JuiceFS。结论限定于这个对照，不声称胜过所有不可变分发系统。各机制实验可以单独失败或只在部分条件有效；组合有效不要求存在额外统计交互。

### 作者指定的三组配置

`native` 指 BrewFS 基础文件系统路径，元数据由原生元数据服务管理；`native-overlay` 在基础能力上增加 Overlay，以共享父版本和私有修改形成工作区，fork 不要求 Packed；`native-overlay-pack` 保持相同工作区语义，将固定下层的元数据改由 Packed 表示服务，可写上层和控制记录仍由元数据服务管理。这是本方案的配置名称，不是三个必须依次执行的阶段，也不把 `native` 解释为本地磁盘。

先用三组共同支持的查名、读写、同步负载测 Overlay 和 Packed 的日常开销，再用具有相同隔离与持久性语义的分支操作测收益。`native` 若没有分支接口，不能填“fork=0”；需明确使用元数据物化适配器，并计入适配工作。`native-overlay` 对 `native-overlay-pack` 的比较固定数据对象、对象粒度、缓存预算和上层实现，分离 Pack 效果；Dynamic block 另设控制维度，不默认与 Pack 联动开启。

名称按作者含义使用；本地源码快照可确认原生 catalog lower 与 Packed lower 的可选绑定，但未出现这三个逐字命名的 CLI 模式。不得把作者命名直接拼成命令，也不能混淆 `WorkspaceLower::Native`、`native_base` 模块和只读布局对照 `native-tikv`。执行时把每组映射到冻结版本的真实命令，并验证 lower 类型、上层路径和对象写入路径；具体源码映射保存在研究记录，论文只讲原理。

## 2. 共用条件与已有材料

- 两系统分时使用同一套 **4 个 RustFS 服务**，独立桶和元数据空间；自建元数据服务和监控，不要求 Kubernetes API。每个客户端拟固定 4 CPU、8 GiB、1 GiB 文件缓存；4 个存储服务各拟 16 CPU、32 GiB，元数据预算 8 CPU、32 GiB，数据库有效内存预算 24 GiB，监控 8 CPU、16 GiB。这些是申请预算，实际 CPU/内存/卷/物理节点分布必须记录。
- 默认客户端主组 4 个；迁移主组另有 4 个已就绪目标。规模扩展到 16/64/128 个客户端，不把容器数当机器数。存储卷数、编码几何、可靠性和服务端预算在比较期间固定；未验证的 2+2 或 4+2 不能写成实测部署。
- BrewFS 在执行开始时读取官方默认分支最新 SHA，随后固定。JuiceFS 使用执行仓库已指定的 CE 1.4.2，构建和配置固定。论文较早的源码快照只提供设计依据，不能代替新版能力验收。实验补丁与上游原版分别标注。
- 元数据同步策略、对象完成条件、缓存、压缩、预读和完整性校验必须匹配。生命周期实验不以本地写返回代替远端确认；完整记录排空后台工作的尾部。
- 7 份归档地址和 SHA256 已快照到 `trace-archives.json`。其中两份 Pytest 是同一道题的两次采集，不能算七个独立任务种类；八次旧观测与这七份完整回放也不能合并成同一采集。
- 当前完整回放器会解析记录并校验内容，其时间不是纯文件系统时间。对照在同一工具、相同校验模式上执行；同时采集客户端/服务端指标，检查回放 CPU 是否先饱和。

沿用执行仓库 `workloads.json` 的两个确定性输入：F1 为 1 GiB、32,768 个 16 KiB 小文件加 128 个 4 MiB 文件；F2 为 1 GiB、64 个分片、262,144 条 4 KiB 记录。字节、路径、权限和版本规则保持原定义，生成后记录实际摘要。

新增小文件元数据输入 M：每文件 1 KiB 唯一确定性内容，每目录 256 个文件，目录再按每组 256 个分层；N=32,768/1,048,576，8,388,608 为资源允许时的扩展。两表示使用完全相同的源文件与数据位置。纯元数据比较关闭数据内联和压缩；默认内联/压缩作为单独的实际配置比较，不能把它的收益算给元数据分组。输入生成不是已经完成的测量。

## 3. RQ1：Overlay 本身的贡献

### fork 与独立修改

从 F1 创建父工作区，先改写 1 MiB、删除/改名各 32 个指定小文件并保存 64 KiB 状态，远端确认后得到父版本 P。所有子分支必须继承这些修改，不能只从原始干净基线创建后称为父状态 fork。

主组一次从 P 派生 1/16/64 个子分支，256 为扩展。每个子分支在固定不重叠 4 KiB 块上写自己的 1 MiB 内容，再保存状态。128/512 MiB 修改作为边界组。分别记录父版本准备、子分支请求、首个正确读、首个持久写和保存确认；父保存不能隐藏在计时前。

内部对照在**不开 Packed**时比较继承元数据与物化当前元数据，保留相同 payload 共享、API、缓存、持久性，不能强迫物化对照复制全部数据来制造优势。外部对照允许 JuiceFS 原生 clone 复用数据块；原生 clone 的元数据工作和排队全部计入。

另生成固定 33 个状态的分支树，每条边都 fork 后修改 1 MiB，总共 32 次 fork/32 MiB 新写入：星形 `parent(i)=0`；四叉 `parent(i)=floor((i-1)/4)`；四条深度 8 的链 `parent(i)=0 if (i-1)%8==0 else i-1`。三组均保留全部状态，核对父、子、兄弟的递归预期清单，避免用指数增加任务数来混淆深度成本。

主输出：fork/保存 p50、p95，每子分支元数据记录与实际字节，上传/对象请求、父子隔离、总创建时间。256 个 fork 是同一批内的操作，不是 256 个独立重复。

### 历史保留

N=1,000/10,000，100,000 为扩展；64 路创建，每状态 1 MiB 修改和 64 KiB 会话文件，确认后关闭执行进程但保留可恢复状态。每档按固定种子抽最多 1,024 个重开并检查状态及指定 4 MiB；完整树核验抽样范围另报。不能把终止记录、墓碑或已删除对象计为历史。

每档创建截止 1,800 s；OOM、错误或元数据有效预算达到 90% 时停止增长，报告实际正确完成数和原因，不称系统绝对上限。删除一半状态、统一保护期 600 s 后，观察 3,600 s 的释放进度与前台干扰；未回收量保留。比较源版本仍保留与可安全释放两种状态，不能删除仍被父/兄弟引用的数据。

## 4. RQ2：Packed 的收益、减压与成本

### 先把三种时间分开

对同一父任务的状态，固定内容、可见性和恢复目标：

1. **native 首次 fork**：暂停/取得一致源版本 → native 版本确认 → 创建子分支 → 首个正确操作。native 所需 seal/固定版本工作也计时，不假定它免费。
2. **packed 首次 fork**：相同起点 → 取得一致源版本 → 构建索引/页面 → 上传并验证 → 发布 → 创建子分支 → 首个正确操作。报告总时间和各阶段；允许实际支持的流水化，但不能相加重叠阶段。
3. **已有版本的复用 fork**：分别复用已确认的 native 或 packed 版本，单独测子分支准备和访问；同时保留此前构建账单。

这些都是 overlay fork，差别是 lower 表示。另做独立只读 native/packed 查询，证明 Packed 无需依赖 overlay 才能产生作用。只有相同内容的**固定版本之间**的比较，才能排除“不可变比可变更容易缓存”这个混杂因素。

### 具体访问收益

使用 M 的两个主规模。每会话 32,768 次查询，消费者 1/16/64；查询表在跑前冻结，包含：

- 随机存在名称查询；50% 存在、50% 不存在的混合查询；按 inode 取得属性。
- 按目录相邻名称查询；目录遍历后逐项取得属性；查询后立即读取对应文件。
- 同目录相邻访问与随机跨目录访问分开；消费者读取相同路径与互不重叠路径分开。
- 冷客户端、仅索引热、元数据热三组。查询后读文件另报 payload 缓存状态。源数据准备和完整树验收若预热缓存，必须重建声明的初态。

逐层计数：native lower 数据库操作、upper/control 数据库操作、对象索引页请求、联合元数据页请求、数据定位描述符请求、payload 请求。报告每次逻辑操作的数据库访问、GET/HEAD 数、字节、解码/校验 CPU、p50/p95 和缓存占用。普通文件系统请求数不能代替数据库请求数。

解释重点是**把固定版本的逐文件查询从中心数据库移到对象页及客户端缓存**，并检查是否以更多冷读、过取、索引和验证成本为代价。额外的不可变逐记录索引对照可以分离“移出数据库”与“联合分组”的收益，但只有同等语义的实现完成后才作为因果证据；没有它时不宣称已完全分解两者。

### 中心数据库和其他工作区的压力

在同一数据库服务上保留独立可写工作区探针，操作为 80% 属性读取、20% 不同文件的更新与同步。先标定两表示在无背景读取时的较低可持续吞吐 r（5 分钟无队列增长且按时完成率≥99%）；探针固定发 `0.25r`，正式比较前冻结。

背景只读请求用同一冻结查询表，以 0/r/4r 的相同到达率向 native 或 packed 版本发送，1 分钟预热、5 分钟计量、最多 2 分钟收尾，每请求期限 2 s。后台消费者最多 64 个，队列增长、超时保留；报告实际发令延迟，发生器不足时不归因于存储。

记录数据库请求/秒、CPU 核秒、内存和持久字节，以及探针按时完成率、队列和 p95。与此同时记录四个对象服务、客户端、网络和缓存资源，确认压力是否只是转移到另一处。

**数据库空间要单独判定。**Packed 可在源记录仍保留时减少查询压力，但不一定减少数据库存储。分别记录原始源保留和通过实际生命周期协议安全退休后的占用；如果实现不能退休，就报告不能退休，不把本地删除记录当成能力。

### 生命周期与更新频率

固定每会话查询表，K=1/4/16/64/256；每生成一个新版本后复用 K 次。连续发布 8 个版本，每次修改 0.1%/1%/10% 文件的属性及内容；每次修改触发的实际扫描、打包、复用、上传、校验和发布工作全部记录。不假定当前实现有增量打包。

版本末次使用后保留 0 或 600 s，T 从取得一致源状态到实际回收；资源不足时记观察截止与残留。按已有 `C_c(K,T)` 分别报告 CPU、请求、网络、数据库/对象驻留字节时间和费用，**不把不同单位相加**。首次可用时间及批次经过时间直接计时，不对并发任务时长求和。

对每个成本指标分别报告 `C_packed,c(K,T) - C_native,c(K,T)`。注明工作负载、缓存与保留政策，报告实测各 K 下的差值及交点；首次为负仅是观察到的最早回本，若非单调或随后变正，也必须保留，不能外推成统一阈值。没有回本就报告没有。频繁重建、少量复用、低局部性、native 缓存已命中，是必须保留的负例。

## 5. RQ3：对象粒度，而不是配置标签

用 F2 的 1/16/64 个消费者，每人固定 1,024 个 4 KiB 记录；相同/不重叠 key 两组，整文件顺序扫描为边界组。补充 4 KiB/64 KiB/1 MiB 对齐和跨边界读取、顺序/分散覆盖写，以及支持时的降级读和修复。

先在相同逻辑写入下，仅改变客户端 g=1/4/8/16 MiB（实际支持值才运行），固定后端布局。再固定对象内容及 S3 请求流，比较后端默认、受支持固定 B 和长度选择策略，以及实际支持的 q 布局。最后在同一对象集合上配对范围读取/整对象获取，固定缓存、合并和预读。

“dynamic block”在本方案中必须落实为实际机制：客户端可配置 g 与后端按已形成对象选择布局不是同一个动作。没有访问驱动的 g 控制器，就不声称 g 会自动随负载调整；自动和默认得到相同布局时是无处理差异对照。

每个新对象记录实际长度及持久化 B/q，核对准入条件。主指标为对象数、请求数、HTTP 读写字节、存储端实际数据/校验读取字节、校验与编码 CPU、远端写完成、修复流量和工具时间。物理字节未采到时填 null。若官方当前后端不支持研究布局，扩展后端实验必须另列版本和补丁，不能混成上游主结果。

## 6. RQ4：部分迁移、冷启动和恢复

主组 4 个源 worker 各 4 个工作区，共 16 个；另有 4 个已就绪目标 worker。选中 M=0/1/4/8 个，按固定排序取等距 ID，目标为下一源组对应的目标 worker。迁移并发 1/4，源目标总资源在两系统间相同。扩展使用 64 源、64 目标，共 256 个活跃工作区，M=16/64/128。

每轮读并核验 4 MiB、改写 1 MiB、保存 64 KiB 轮次状态；选中工作区共执行 20 轮。在第 5 轮工具结束、句柄关闭后进入两种入口：已远端确认；仍有 1/16/128 MiB 待保存修改。后者从迁移请求开始计入排空、固定版本、必要打包/发布，不能只计目标打开时间。native 和 packed 路线分别跑，不以 packed 作为迁移前提。

所有选中者在共同 t0 暂停，等待迁移槽位也计入暂停。邻居不暂停，每 5 s 请求一轮，持续 600 s，单轮期限 120 s、收尾最多 300 s；不迁移配对组使用相同工作量、屏障与时间表。目标首个正确操作期限 t0+600 s，选中者完整续跑期限 t0+900 s。额外用目标冷/暖缓存分组，禁止先全树扫描再宣称冷恢复。

JuiceFS 在目标打开原目录，允许已有远端状态和缓存复用，不为迁移重新 clone 或复制整树。BrewFS 打开所选已确认状态。安全停止源、取得目标写权、状态核验及恢复后读取都计入。指标用同一协调器的单调时钟：请求/排队、排空与发布、释放旧写者、目标接入、首个正确操作和最终完成；另测迁移字节、邻居吞吐及 p95，相对不迁移配对批次报告。

故障验证分开做：保存确认前中断、确认后中断、源仍能到达存储但失去协调连接、目标恢复中断。每点每表示 20 次正确性尝试。核对确认内容、版本和轮次、父/兄弟状态；实际尝试旧身份写入/发布并由独立客户端读回。外部终止进程、应用提交检查、存储端拒绝分别记录，不能把协调器不再派任务当成存储 fencing。源/目标若不能证明位于不同节点，只称跨容器交接。

## 7. RQ5：完整文件负载与实际 Agent

**固定工作量：**7 份完整 trace 各 8 次，共 56 个任务，4 个 worker；并发 1/4/16。同一任务表、初态、请求顺序、输入和校验方式；task i 使用 `case[i%7]`，worker 为 `floor(i/7)%4`，重复时循环置换 worker 编号。每任务准备、回放和终检总期限 1,800 s，所有并发共同观察上限 `56×1800+300=101100 s`，不能低并发给长窗口、高并发给短窗口再比较正确完成数。准备/执行/终检分别计时，另报从提交到最终有效结果。

**规模：**worker=4/16 为主组、64/128 为扩展，每 worker 并发 4，每 worker 把 7 份 trace 各执行一次，总任务量 7W。固定后端预算、每 worker 资源和缓存，报告正确任务/秒及逐 case 时间；工作量增长，不能把批次时长当固定工作量加速比。按 7 种 case 的流量分别看结果，防止较长的 Django 独占汇总。

每系统每格先 3 个独立批次，两个系统顺序随机、按同一输入/资源分配配对。外部比较子集为 18 批、1,008 次回放；详细主组再加入native和Pack配置，总计36批、2,016次回放；4 档扩展全做共 24 批、8,904 次回放。先做单任务和小规模，再决定资源允许的档位；未做档位保持未执行。重复同一 trace 不增加任务种类，批内任务不当独立批次。

**真实会话验证：**沿用已冻结任务清单中的 `pytest-dev__pytest-10051` 与 `sympy__sympy-11618`。在第 3 个完整工具结果后保存父状态；fork 4 个子 Agent 各自继续，或迁移一个原会话，分别与不 fork/不迁移配对。保留会话历史、文件、已完成工具结果和剩余预算；不得重置预算、重新给初始提示后当作续接。每题每系统每条件 3 次，模型/路由/提示/工具与评分材料固定。每题总模型预算和启动后 30 分钟期限沿原任务定义，fork 的 4 个子分支共享剩余总预算，具体分配在运行前冻结为等分。

本项需要真实会话 fork/续接接口；不能用复制 session.bin 代替。没有该能力时，文件状态机制实验继续，但不报告 Agent fork/恢复成功。记录子会话 lineage、迁移后首个真实工具结果、最终评分、重复工具调用和模型成本；采集/评分过程与计时边界分开。文件回放优势不等于模型任务提速。

## 8. 计量、成本和结论

- 每 worker 采集 CPU、限流、内存、可归属 I/O 和网络，1 s 一次；客户端文件系统计数 1 s，元数据服务 5 s，4 个 RustFS 经 OTel 到 Prometheus，独立结果接收器持久化事件和摘要。沿用执行仓库 `observability.md` 的采集链路；实际指标名与可用性先核验。
- 采集范围必须区分 lower 查询、可写 upper、版本/租约控制、打包构建、读取和回收。记录元数据数据库负载下降时，对象服务与客户端增加了多少工作。不能把 Redis命令数直接当逻辑查名数，不能将 HTTP 字节称物理读盘字节。
- 共享构建和对象计一次，驻留空间按实际对象区间并集计费。源副本、保留历史、缓存、索引、临时构建峰值都记录；读优势和保存/写优势分别成立，不能互相代替。
- 每格 3 批先报配对原值、中位数和范围。需推断性结论时，依据独立方差 pilot、在比较前冻结批次数，不用百万请求冒充样本。容量拒绝、超时、错误和缺指标都保留；不把所有任务已退出当所有任务正确完成。
- 对完整任务用截止时正确完成数曲线和正确任务/秒。全成功时才报全成功 makespan；未全成功报告未完成及截止限制，不把确定失败伪装成普通无信息删失。

论文主图顺序建议：① native overlay 的 fork/保留成本；② Packed 的数据库减压与旁路成本；③ 首次 fork 和 K/更新频率下的生命周期交点；④ 粒度对逻辑请求→HTTP→物理工作→工具时间的影响；⑤ 迁移阶段与邻居影响；⑥ 固定工作量和规模结果。图必须来自真实运行，当前只设计图的横纵轴。
