# 测量口径（强制）

本文件规定 **overlay / flat-v1 / packed 三臂对比的唯一有效口径**。
任何与本文件冲突的旧口径作废。CSV 契约见 [`validate.py`](validate.py)，汇总见 [`summarize.py`](summarize.py)。

## 1. 两种口径，只有一种能下结论

| 口径 | 定义 | 用途 |
| --- | --- | --- |
| **W（主口径）** | **下层已预热**后的稳态 | **唯一可用于结论、验收、论文数字的口径** |
| C（参考口径） | 清页缓存 + 冷下层 | 只用于说明「冷启动成本有多大」，**不得用于结论** |

### 为什么必须区分
实测（2026-10-29，同一二进制 `80ddaf7`、同一机器、各 3 次中位）：

| 路径 | W 口径吞吐 | C 口径吞吐 | 差异 |
| --- | ---: | ---: | --- |
| `flat-v1` | — | 45.967 MiB/s | — |
| `overlay + native`（focused 热） | **78.570 MiB/s**（损耗 9.0%） | 19.874 MiB/s（损耗 56.8%） | **4 倍** |
| `overlay + packed` | 待测 | 9.686 MiB/s（损耗 78.9%） | — |

**同一份代码，口径不同，损耗率从 9% 到 57%。** 用 C 口径下结论会系统性地冤枉 overlay（尤其 packed），
因为它把「冷取下层 + 冷建 chunk 索引 / read plan」这些**一次性成本**算进了每次读。

## 2. W 口径怎么做（三臂一致）

1. **预填**：写入固定工作集（当前为 4 × 512 MiB，确定性内容），`fsync`，
   等 `brewfs_writeback_dirty_bytes` / `live_dirty` / `pending` / `stage_inflight` / `remote_inflight` 全部归零。
2. **下层预热（一视同仁，不可省）**：
   - `flat-v1`：顺序读一遍 + 随机读一遍
   - `overlay + native`：**随机读 2 遍**（第 1 遍读入 lower chunk 并建立 read plan）
   - `overlay + packed`：**随机读 2 遍**（让 packed lower 的 chunk / 索引 / 计划就位）
3. **预热到位判据**：第 2 遍吞吐与第 1 遍差 **< 10%**；否则继续预热，直到满足。
4. **主体测量**：预热后连续 3 × 30 s，**之间不清页缓存**，取中位。
5. **C 口径**（可选）：放在最后单独做 1 次，`sync; echo 3 > /proc/sys/vm/drop_caches` 后立即测，
   报告中必须显式标注。

> 生产语义依据：线上读请求基本落在本地（下层 chunk 已在块缓存或本地对象副本），
> 冷取下层不是每次读都要付的成本。

## 3. 阶段分解（判断「损耗花在哪」的唯一方式）

**`fio` 的 `clat` 含排队时间（`numjobs × iodepth`），不能用于阶段分解。**
必须用进程内分段计时，六段定义固定如下：

| 段 | 边界 |
| --- | --- |
| `fuse_dispatch` | FUSE 请求接收 → worker 开始处理 |
| `resolve` | 两层解析（workspace / head epoch / inode） |
| `row_cache` | 行缓存查询 |
| `redis_meta` | Redis 后端读 API（get / bounded get-many / scan） |
| `extent_plan` | extent 覆盖计划构造（含 `prepare_unified_read` / packed 路径） |
| `data_path` | `execute_into`（块缓存查找 + 对象读取等待） |

硬要求：
- 计时开关由环境变量控制，**关闭时零开销**（`OnceLock<bool>` 只判一次）；
- 开关关闭 vs 打开的吞吐差 **< 3%**，须在报告中给出验证；
- 报告同时给「平均」与「最慢 1%」两组占比 —— 二者常不同
  （实测 native：平均 Redis 60.4% / 数据 36.1%；最慢 1% Redis 33.2% / 数据 65.4%）。

## 4. 报告必须产出

- **表 A（W 口径，主）**：三臂 × 六段（平均 µs + 占该臂合计 %）+ 吞吐 + p99
- **表 B（C 口径，参考）**：三臂各 1 次，显式标注
- **Redis 命令数 / 读**：三臂各一列；W 口径与第 1 遍预热分开记
- 预热第 1 遍 vs 第 2 遍吞吐（证明「热到位」）
- 仪器化开销验证（§3）
- 未验证项清单

## 5. 禁止事项

- ❌ 只用 C 口径数字下结论或做验收
- ❌ 用 `clat` / `p99` 反推阶段占比
- ❌ 只跑 `fio` 单一工具就宣称「完整对照」（至少覆盖随机读、顺序读、混合、元数据、目录）
- ❌ 用 sqlx / sqlite 元数据后端做性能对比（与 Redis 后端不可比）
- ❌ 在测量机上同时跑编译或其他负载

## 6. 当前基准数字（用于自检，不是结论）

同一二进制 `80ddaf7`、`ecs.g6.2xlarge` / 200 GiB ESSD、`fio 4KiB randread numjobs=4 iodepth=32 direct=1`：

| 口径 | flat-v1 | overlay + native | overlay + packed |
| --- | ---: | ---: | ---: |
| W（focused 热） | 86.334 | **78.570**（91.0%） | 待测 |
| C | 45.967 | 19.874（43.2%） | 9.686（21.1%） |
| C（p99 ms） | 55.312 | 221.250（4.0×） | 480.248（8.7×） |

若实测与本表偏离 > 15%，先检查口径是否一致，再看环境差异。
