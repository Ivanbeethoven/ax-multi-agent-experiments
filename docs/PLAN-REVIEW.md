# 实验方案：四个问题

状态：用户已确认；每个条件运行一次，先完成四组流程。

| 组 | 要回答的问题 | 主要对照 | 对应创新点 |
|---|---|---|---|
| 1. 基础 fio | 大块顺序与小块随机读写能否更快，实际存储读写能否更少？ | BrewFS Native、JuiceFS Redis；附带块尺寸和 Dynamic 比较 | 可变对象块与小范围读取 |
| 2. fork 与 Overlay | 创建子工作区有多快，增加一层 Overlay 带来多少读写开销？ | BrewFS fork、JuiceFS clone、JuiceFS Overlay | 共享父数据、私有增量 |
| 3. Packed | Packed 能否加快 10 万只读小文件的准备和读取？ | Native、Packed、JuiceFS Redis、JuiceFS TiKV | Packed 索引与整包读取 |
| 4. 多 Agent 回放 | 多个 Agent 同时工作时，吞吐和存储开销如何变化？ | BrewFS 工作区、JuiceFS Redis、JuiceFS Overlay | 共享数据、私有修改与 Dynamic |

## 1. 基础 fio

在 fork 出来的空工作区中生成 32 GiB 文件，再直接读写这些文件。测试数据属于当前可写层。输入准备在计时前完成。

固定 8 个 fio job，使用 `direct=1`：

| 负载 | 应用请求 | 所有 job 合计工作量 |
|---|---:|---:|
| 顺序读、顺序写 | 1 MiB | 各 8 GiB |
| 随机读、随机写 | 4 KiB | 各 256 MiB |

- 主比较：BrewFS Native 与 JuiceFS Redis，共四种负载。
- Dynamic 比较：BrewFS 在同四种负载下关闭 Dynamic。
- 块尺寸比较：只在随机读、随机写中增加固定 B=64 KiB、4 MiB，其他参数保持不变。
- 读取从客户端冷缓存开始；写入每累计 64 MiB 执行 fsync，最后等待上传完成。
- 指标：吞吐、IOPS、P99、应用/S3/磁盘读写字节。记录实际 B/q。

共 16 组系统配置，各运行一次，合计 **16 次运行**。复用 fio 配置生成、`c1-io-helper`、挂载和指标采集代码。

## 2. fork 与 Overlay 开销

父数据使用与第 3 组相同的 10 万个 4 KiB 文件。

**fork 性能：** 分别创建 1、16、64 个子工作区。比较 BrewFS fork、JuiceFS clone、JuiceFS Overlay。分别记录父数据准备时间、批量创建时间、单个子工作区就绪时间和新增存储空间。

**Overlay 开销：** 在单个子工作区中冷缓存读取固定的 1 万个文件，再覆盖其中 1,000 个文件；与同一系统直接读写父工作区的结果比较。两组从相同内容开始，分别记录读取时间、首次覆盖写时间、元数据请求与实际上传字节。

读写直接父工作区的测试使用独立副本。检查父数据、子工作区和兄弟工作区的修改隔离。

fork 共 9 组配置；直接父工作区增加 3 组配置，子工作区读写复用单子工作区测试。各运行一次，共 **12 次运行**。本组保持正常缓存和 Dynamic 配置。

## 3. Packed 只读小文件

固定 100,000 个 4 KiB 文件，每目录 1,000 个文件，所有系统使用相同内容。Packed 数据集保持只读。

**准备与上传：** Native、Packed、JuiceFS Redis、JuiceFS TiKV，从同一个本地目录开始，使用 8 个准备 worker，计时至其他机器可读。Packed 的扫描、打包、上传和注册均计入。

**读取：** 固定 32 个读者，每个读者读取全部文件两遍，分别记录首次冷读与第二遍读取。

| 读取组 | 设置 |
|---|---|
| BrewFS Native | 逐文件元数据，TiKV，正常缓存 |
| BrewFS Packed | 整包缓存开启，Dynamic 开启 |
| BrewFS Packed | 整包缓存关闭，其他参数相同 |
| JuiceFS Redis | 正常缓存 |
| JuiceFS TiKV | 正常缓存 |
| BrewFS Packed | 整包缓存开启，Dynamic 关闭 |

Native 和 Packed 使用同一套 TiKV 服务保存各自需要的可变元数据。JuiceFS 分别采用 Redis 与 TiKV。

Dynamic 关闭组重新生成其对象，同时记录准备和读取时间。主要指标为准备总时间、首次 64 文件读取时间、每遍读取时间、元数据请求数、S3 请求数与下载字节。

共 5 组准备、6 组读取，各运行一次，合计 **11 次运行**。复用现有导入工具、`c3-loader` 和原始指标采集代码。

## 4. 多 Agent trace 回放

使用 [trace-inputs.json](../configs/trace-inputs.json) 中现有八类主负载，以及现有 Rust `full-fuse-replay` 工具。

- Agent 数量：**1、8、16、64**。
- 1 个 Agent 顺序执行八类任务；其余规模按相同比例分配八类 trace。各系统在同一规模下执行相同任务集合。
- 工具调用边界之间加入固定种子的 **1～7 秒随机等待**，保留任务内部文件操作顺序。
- 主比较使用 BrewFS 工作区、JuiceFS Redis、JuiceFS Overlay。缓存与预读使用正常参数。
- **仅在 64 个 Agent 时增加一组关闭 Dynamic 的 BrewFS**，与开启组保持相同 trace、随机等待、资源和缓存设置。
- 指标：任务/小时、各类任务完成时间 P50/P95、文件操作数、实际读写量、重复读取比例、元数据请求、S3 流量及 CPU/内存占用。等待时间与文件操作执行时间分别保存。

主比较 12 组配置，Dynamic 增加 1 组，各运行一次，共 **13 次批量运行**。复用现有批量挂载、trace 边界计划和回放脚本。

## Dynamic 的统一比较方法

第 1、3、4 组的 Dynamic 开启条件访问修改版 RustFS 四节点集群（端口 9000）；关闭条件访问原版 RustFS 1.0.5 四节点集群（端口 19000）。两套服务使用相同四台主机、相同 CPU/内存预算和独立数据目录。每套重新写入自己的输入对象；客户端版本、缓存、负载与随机种子相同。结果记录两套软件版本、实际端点和持久化 B/q。

服务配置见 `configs/rustfs-backends.json`。修改版的动态功能保持开启；执行器按条件选择端点，指标同时选择 9464 或 19464。

第 1 组额外的固定 B 比较保留子块读取，单独观察块尺寸影响。第 3、4 组各只增加一个 Dynamic 关闭条件。

## 机器、缓存和结果

使用现有六台服务器，存储访问走 eth0 直连。最高 64 个活动 Agent。fio 每挂载使用 16 GiB 内存与 16 GiB 磁盘缓存总预算；其余三组每工作区使用 4 GiB 内存与 8 GiB 磁盘缓存总预算，各系统采用正常性能配置；具体容量、上传并发和预读参数随结果保存。

TiKV 部署在现有机器，并单独预留服务资源。正式计时条件依次执行；准备、编译和结果处理安排在计时之外。

六台主机每 5 秒采集 CPU、内存、磁盘、网络及服务指标，阶段开始和结束额外记录快照。应用完成、上传完成、冷挂载读取分别计时。内容比较放在计时后。

新结果统一放 `results/<run-id>/01-io/`、`02-fork/`、`03-packed/`、`04-agent-replay/`；每组保存配置、版本、原始输出、指标采样和汇总。历史结果放 `archive/results/`。

合计 **52 次实际运行**，全部包含单次运行。每组使用单独配置和说明，共用准备、挂载、采集、监控与结果整理代码。
