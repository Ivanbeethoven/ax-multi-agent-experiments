# B 组 C1 混合读写：容量事故与重跑门槛

原 `mxb01` 的 Off1、On1 完成；On2 的 fio 退出 0，但对象采样在第 28 份后中断，结束检查连接被拒绝。剩余三轮和正式 C1 均未启动。此次分析只读协调者已有归档和本地证据；没有启动 B、访问工作节点、清理文件或调整配置。[原失败和收尾记录](../b-c1-on2-failure-recovery-01/README.zh.md)保留原判定。

## 准备和计时写入分开

原 64 MiB 的 4 KiB CRC 基线在 05:15 UTC 前已一次性生成并冷读验证。[原资格回执](../pool-b-services-actual-01/c1-qualification.json)和冻结 `fio_workload.py` 显示，该次 prepare 用顺序 `write`、`--fsync=0 --end_fsync=1`；逐操作同步属于后来的 `measure` 合同。Off1 和 On1 的轮内准备分别耗时 0.384、0.382 秒，都是 `juicefs clone -p <base-4096> <child>`，然后对克隆出的文件和目录各做一次同步。On2 调用了同一 SHA 的 `copy-fio` 且退出 0；原批在后面失败，没有回传这一轮独立的 copy/result。这里没有每轮用 fio 重新填满 64 MiB 的步骤。

Off1、On1、On2 的计时工作相同：64 MiB 总 I/O、4 KiB、随机混合读写、seed 9173、`rwmixread=75`、同步深度 1、`--fsync=1`。三轮 fio 各自实际读 **50,479,104 B / 12,324 次**，写 **16,629,760 B / 4,060 次**。fio 的 `sync.total_ios` 字段各为 **16,382**，与写次数不同，分别保存。计时阶段不允许创建文件；冷验是读。跨轮 RustFS 流量不能直接归到一次测量的这些应用字节上。

## 能证明多少空间变化

同一对象节点、同一 RustFS 进程（PID 4744、启动 tick 63431、同一 boot）。四盘顺序为 `/srv/ax-objects-0` 至 `-3`，容量列取 `statvfs.f_bavail × f_frsize`，均为字节。C2 最后一份采样是最近的已有起点，距 C1 Off1 开始约 231 秒，中间还有 C2 的归档和 C1 启动准备，不能称为 C1 精确起点。

| --- | ---: | ---: | ---: | ---: |
| [C2 正式最后一份](c2-objects-sample-199.json)，12:05:55 | 42,491,367,424 | 57,296,474,112 | 57,296,445,440 | 57,296,457,728 |

从 C2 最后一份到 On2 sample 28，四盘净占用分别增加 **42.432 / 36.757 / 36.757 / 36.756 GB**，合计 **152,701,939,712 B**。同一 RustFS 的 HTTP 请求体累计增加 **167,149,912,064 B**，成功 PutObject 增加 **48,682** 次、DeleteObject 增加 **27,510** 次。这是 **C2 收尾至 C1 On2 前段的服务端计数差**，包含多轮和可能的后台活动。它既不是单轮 JuiceFS 上传字节，也不是 RustFS 写盘总量、最终净占用或空间上界。事后客户端上传债务为零也不表示 RustFS 已释放全部磁盘空间。

在 On2 第 20 至 28 份之间的 41.447 秒，盘 0 减少 972,484,608 B，另三盘各减少约 927 MB，三盘合计 **2,782,277,632 B**。对象观测原文只写盘 0；第 28 份文件内容合计 5,664,916 B（不含 sample.json、目录等）。历史原文加重了盘 0 的压力，但解释不了另三盘的净增长。第 28 份时 RustFS 容量 exporter 的最近成功快照比对象本地 `statvfs` 旧约 23.6 秒；盘满门槛使用本地四盘值。原事故记录称后续四盘一度 `df` 可用为 0，13:02 的存档记录了随后空间；没有找到对象采样器的直接 ENOSPC 栈，不能将退出原因定为已证实。已留档日志中的 4 MiB 对象名和 heal 错误是调查线索，不能量化每阶段实际写入。

On1 的协调者原审计只记录 150 份对象采样、四个阶段标记和结束摘要 SHA。协调者没有原首尾样本的容量或客户端 `juicefs_object_request_data_bytes` 值，现有证据不能拆出 clone、计时、排空、冷验四阶段的上传或占用。B 停机期间也没有读取工作节点上的原文。

原 C1 请求及校准执行路径没有四盘开跑前或轮间的空间门禁。此前 C2 的容量回执用一次基础导入增量（每盘约 141 MB）估七份副本，再保留 20%；它不覆盖 C1 混合写入、后台回收暂存、四个 On/正式的采样和归档。不能沿用 C2 通过的结果给 C1 放行。

## 重跑前先回收可以证明的副本

协调者已有 C2、C3、C4 的 12 个 B 对象角色归档及通过的成员核验回执；只读取压缩包开头的 manifest，未读样本载荷。它们覆盖的 `o/<tag>` 普通文件逻辑字节分别为 **4.388 / 1.341 / 3.033 GB**，合计 **8,762,614,136 B**。原归档工具另在同盘复制原文到 `retained-calibrations/<bundle>/<tag>/raw/`（C2/C3 校准）或 `evidence/<tag>/`（C2/C3 正式及 C4）。两套都仍在时，候选原文共 **17,525,228,272 B**，不含压缩包、其他文件或目录。此数是历史逻辑量；未验证现有工作节点路径、实际 `st_blocks` 或可回收总量。归档的精确 tag、路径、包 SHA 与逻辑大小见 [sources.json](sources.json)。

四个文件系统各 60,070,604,800 B；20% 预留要求每盘至少 **12,014,120,960 B** 可用。仅以 13:02 已有复查为起点，四盘距预留线分别还差 **11.419 / 0.991 / 0.984 / 1.029 GB**，未计新负载。历史原文副本都在盘 0，无法抬高另外三盘的空间。即使盘 0 确认可回收 17.525 GB，整个批次的容量也未得到证明。若原 C2 末至 On2 的盘 0 占用不变，单是容纳这个已经观测到的时点并保留 20%，也需要至少 75.015 GB 的可计文件系统容量；这不是完整七轮的建议盘型。

1. 先在协调者校验候选的归档及公开读回。只有在需要继续 C1、已确认无冲突且允许唤醒时，先短时唤醒 B 对象节点，核对四盘 `statvfs`、inode、同一设备和挂载、已归档目录的 `st_blocks`，并取 On1/On2 的对象采样首尾及阶段标记。已保留数据能提供诊断，无需启动负载。按本轮报价，仅对象节点启动的增量约 ¥1.80/小时，10–15 分钟约 ¥0.30–0.45；9 块盘仍按 ¥0.966/小时计费。
2. 按完整成员 SHA 和物理锁，只回收已关闭、已验证的同字节观测副本。对象目录、Q 下的源回执、历史 C1 失败原文和未核验路径全部保留。另三盘的缺口只能靠确认的 RustFS 自然回收，或另行审定并通过 JuiceFS 删除已验证无保留依赖的过期子工作区；不能用 `rm` 直接删 RustFS 分片。重新量各盘的可用空间，不能把未来 GC 当成已有空间。
3. 使用独立的非正式资格轮测量每盘的最大净占用增量、排空和回收后的残留；在准备、计时、排空、冷验和归档边界分别记录客户端上传、RustFS 请求体、`diskstats` 写扇区及观测原文实际块占用。批次预算按每盘累加前轮保留增量及当前轮峰值；在每一轮开始时，再用当时实测可用空间扣除当前轮的峰值预算，确认仍有 20% 预留。盘 0 另计原文、复制和压缩包。不能用一次短窗口线性外推完整批次。资格失败保留原档并停，不接着跑下一轮。
4. 资格通过后才以全新 attempt 完成原顺序六轮校准（关→开、开→关、关→开）和正式轮，保持原 fio、CRC、冷验、5% 门槛及上报指标。若调整基线准备或盘布局，记录为新的准备条件并从第一轮重测；原 Off1/On1 不与新轮混用。优先在现有盘上通过清理与实测门槛；若还不足，再按四盘各自的实测峰值讨论最小扩容。
