## 随机写的一致性检查阻断提交

标准参数为每文件 512 MiB、4 个文件、20 秒、4 MiB io_uring、深度 1。基线正式轮前两个顺序写场景通过，第三个 `randwrite/direct=0` 冷重挂 SHA 不同，随即停止。精确复现按候选 402 → 基线 403 的顺序进行，两臂均有 2/4 文件不一致；长度均正确，严格排空计数为零，未见上传/恢复失败及服务端 ERROR/HTTP 5xx。旧进程正常退出，新进程使用空缓存、相同二进制及等价参数。

五个保留的 sealed 文件共 20 MiB，其原始字节精确覆盖两臂全部差异：候选 12 MiB、基线 8 MiB，均为 64 MiB chunk 内偏移 60 MiB 的末尾 4 MiB。每个差异段的 sealed 字节等于旧缓存读出的内容，与冷读不同。fio 3.39 的缓冲时间戳解码显示，20/20 段冷读内容时间更晚。这支持旧 SSD 暂存覆盖新内容的解释，但不把暖读当成内容真值，也不凭相关性认定具体竞态已获证明。

源码发现一个可发生的完成顺序：元数据写已开始且仍在等待，上传先完成，清理因尚未 Committed 跳过；元数据随后成功只发布 Committed，不补清理。该候选需要真实 FileWriter 的可控时序 RED/GREEN 证明。标准场景未开启 end_fsync，故这里记录的是正常关闭、严格排空及正常卸载后的可见内容变化，不声称已证明显式 fsync 数据丢失。

## 环境与批次边界

两臂基于 `ca07159f3da4b670e4aeb878faef928e69bc1634`，同一阿里云 r7 8 CPU / 64 GiB 主机，固定工具链、release 参数、4 个 Cargo features、服务镜像、预算与脚本。此历史候选实际 feature 仍叫 `workspace-overlay`，不回填新名称。服务为 RustFS `f4ed2025`，四个动态开关开启、客户端 hint=auto；四个逻辑目录共用一块 SSD，并显式跳过磁盘身份检查。本批不验证独立磁盘容错或分布式 C3/C4。

早先单 `/data` 配置在较大对象上实际返回 InternalError，即使 dirty=0 也不具备正确性资格；该批旧 CPU 数字全部作废。后来的 EC4 结果独立记录。历史重复 fio job、代理写方法、准备阶段提前打开目标文件等脚本问题的失败证据同样保留。
