# B 池 C1 混合读写：新盘小试

2026-11-12，复用 B 池三台实例，另挂四块 100 GiB PL1 临时盘。JuiceFS 1.4.2、BrewFS Flat 和 RustFS 按[版本与资源计划](plan.json)核验。两臂依次使用同一组物理盘、同一 RustFS 进程、同一份 64 MiB 输入、4 KiB 随机混合读写、种子 9173。每臂用新桶和 Redis 库。旧盘、受保护副本和旧验收不变。

| 结果 | JuiceFS | BrewFS Flat |
| --- | ---: | ---: |
| fio 计时段 | 765.425 s | 38.316 s |
| 应用读 / 写 | 50,479,104 B / 16,629,760 B | 相同 |
| 读 / 写操作 | 12,324 / 4,060 | 相同 |
| 两次原生零上传债务 | 通过 | 通过，保留原文和 drain-end |
| 冷重挂后完整 CRC 与退出回执 | 通过，64 MiB | 回执不全 |

BrewFS 的计时进程退出 0，测量挂载也正常卸载。第三次冷重挂后，fio 记录被 SIGTERM 中断，只读了 46,387,200 B，缺少完整 CRC 和冷验退出回执。控制器几乎同时收到同一输出目录已存在的拒绝；第一条 ECS 停机请求晚约 9 秒。现有材料没有记录信号发送者或重复入口，不能认定为文件系统 CRC 失败。[时间线与原始输出哈希](termination.json)已保留。启动器已改为一次提交、独立读取实际服务身份和最终关闭回执；该修复只通过本地测试，未另开云机。本次只报告两份计时原始值和一份完整关闭，不计算加速倍数，不替代旧 C1 的 9/10。

对象节点留下 412 个四盘采样。最少可用 80.932 GB，无容量停止。JuiceFS 整臂前后四盘各净占约 18.746 GB，四盘设备写计数合计增加 201.923 GB；这里包含准备、测量、冷验和后台活动。两节点未报告时钟同步，所以不将设备计数切到 fio 计时段。这个实测只能用于单轮容量预算，不能按比例放行完整七轮。
