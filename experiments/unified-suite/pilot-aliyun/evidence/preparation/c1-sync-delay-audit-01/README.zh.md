# C1 随机写：约 100 ms 同步延迟来自哪里

本次只看原正式样本和它实际使用的 BrewFS main `622736b0a31caaa9007445886e626a2458bc316a`。未重跑，也未变更冻结计划。

| 正式原档 | BrewFS flat | JuiceFS |
|---|---:|---:|
| fio 4 KiB 随机写同步 P50 | 108.528 ms | 6.717 ms |
| fio 1 MiB 顺序写同步 P50 | 10.945 ms | 9.503 ms |
| 随机写：RustFS PUT 服务端记录的平均耗时 | 2.230 ms | 33.305 ms |

BrewFS 的随机写共记录 16,384 次 FUSE `fsync`，累计 1,772.541 秒，平均 108.187 ms。相同角色各自的起止采样、原文 SHA256、计数和时间总和见[原档指标差值](marked-telemetry.json)。RustFS 值是服务端聚合统计，可能受指标导出延迟和后台操作影响，不能和单次 FUSE `fsync` 一一相减。它没有显示一个能解释约 108 ms 的普遍 PUT 服务端延迟。

首要线索是 **小写入合并的默认 100 ms 等待**。在上述提交：

- [默认参数](https://github.com/brewfs/brewfs/blob/622736b0a31caaa9007445886e626a2458bc316a/src/chunk/store.rs#L597-L604)：合并上限 64 KiB；窗口配置缺省为 0。
- [合并队列](https://github.com/brewfs/brewfs/blob/622736b0a31caaa9007445886e626a2458bc316a/src/chunk/store/coalesce.rs#L256-L284)：组满会立即上传；第一个小写入到来且组未满时，配置值 0 代表采用 100 ms 截止时间。调用方等待该组上传。
- [进入合并的条件](https://github.com/brewfs/brewfs/blob/622736b0a31caaa9007445886e626a2458bc316a/src/vfs/io/writer.rs#L4330-L4387)：Redis 元数据支持、先上传后提交，且冻结的写入片段满足大小等限制。归档配置与这些条件相符。单任务 4 KiB 写完就同步，组难以填满；1 MiB 写超出默认阈值。

源码路径和实测数量级吻合，原档没有每次同步的队列分支或截止时间命中记录。不能判定每次同步都走过该路径；提交循环另有条件式的 100 ms 通知兜底，同样未逐次记录。若后续要验证，单列诊断：固定版本、输入、同步频率和缓存，只切换合并策略，同时记录进入合并、凑满或超时、PUT 和提交时刻。若禁用合并后仍出现同一延迟平台，继续查提交通知和其他等待。
