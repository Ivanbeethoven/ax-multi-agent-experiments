# 每轮开始前的空间检查与清理

适用于原冻结 C1–C4。**每次 Off、On 校准和正式测量都单独检查**，不能只在整个批次开始时检查一次。清理在计时外完成；负载、原始采样、冷读校验和验收门槛不变。

## 固定顺序

1. **上一轮退出。** 确认负载和采集进程结束、上传排空、挂载卸载、原始结果落盘。持有本池的物理资源锁后才能维护；其他池仍在使用的共享磁盘、服务和链路不得占用。
2. **先归档。** 校验压缩包及逐文件 SHA256；允许删除的原文还须有协调者副本、OSS 完整读回 SHA256 和匿名访问检查。失败轮同样保留结果，不能因失败而直接清空。只传到 OSS 但没核验不算完成。
3. **列明删除对象。** 清单逐项记录主机、启动身份、磁盘设备、绝对路径、所属旧轮次、实际分配空间、对应归档及 SHA256。先 dry-run，再按相同的目标路径和归档校验值执行；不按目录年龄或通配符批量删。
4. **清理后重新量。** 读取每块盘的实际可用字节和 inode、Redis 内存与 AOF、协调者输出盘。不能把预计可回收量、逻辑文件大小或尚未发生的 GC 当成空闲空间。
5. **检查下一轮峰值。** 空间够才启动这一轮；不足则停止派发，先归档清理或核算最小扩容，不重跑碰运气。

每轮在 `/srv/ax-pilot-control/preparation/storage-<pool>-<attempt>/` 留下清单、dry-run、实际清理结果、清理后快照和容量结果。没有文件需要删除时记录 `not-needed`，仍须做容量检查。

## 可以清什么

| 数据 | 处理 |
|---|---|
| 已结束、已完整归档的 `o/<旧tag>` 采样原文 | 核成员、采样进程退出、实际设备后可回收；本轮和后续校验仍引用的路径保留 |
| `evidence/<旧tag>`、`retained-calibrations/.../raw` 中的重复暂存 | 与已验证归档逐成员一致后可回收；不能直接删整个父目录 |
| 旧实验的私有工作区 | 先证明后续轮次、父子隔离检查和归档均不再依赖，再通过文件系统自己的接口删除；实际回收多少以之后的磁盘快照为准 |
| 不可变基线、输入 trace、会话检查点、原结果/回执、状态库 | 不进入逐轮清理清单；批次结束后的云盘释放另按完整归档收尾流程执行 |
| RustFS 分片目录、Redis 数据文件和 AOF | **不得直接删除。** 对象清理由相应文件系统管理；Redis 重写或对象 GC 不能与计时重叠，也不能预先抵扣空间 |
| 正在测量、排空、冷读或归档的数据 | 不清理 |

当前可执行的两个回收脚本仅覆盖已审定的 A 组路径，**不是任意目录清理工具**：

- [`reclaim-closed-object-observer.py`](scripts/reclaim-closed-object-observer.py)：已结束的 A 组 C1 对象节点 `o/<tag>`；需要原两池锁，apply 必须绑定同一请求和 30 分钟内的 dry-run。工具核 OSS 完整回读与匿名 HEAD。
- [`reclaim-object-evidence-staging.py`](scripts/reclaim-object-evidence-staging.py)：持 A 组原锁，处理已独立核验的归档暂存副本。dry-run 请求为 `apply:false`，执行请求为 `apply:true` 并带 `--apply`；两份请求的路径与归档校验值须一致。此工具尚未强制绑定 dry-run 回执，也不自动验证 OSS，使用前仍须完成第 2、3 步，不能直接当作自动清理入口。

首个脚本的实际调用形式如下，变量均来自本轮清单，不填通配路径：

```bash
python3 reclaim-closed-object-observer.py \
  --request "$request" --sha256 "$request_sha" --out "$dry_out"
python3 reclaim-closed-object-observer.py \
  --request "$request" --sha256 "$request_sha" --out "$apply_out" \
  --apply --dry-run "$dry_out/result.json" --dry-run-sha256 "$dry_sha"
```

## 下一轮要留多少空间

每块盘分别满足以下条件，inode 也做同样检查：

```text
清理后实际可用量
  - 下一轮数据最大新增量
  - 原始观测数据
  - 归档和解包同时存在时的额外占用
  >= 该盘总量的 20%
```

对象节点四块盘逐块判断，不能把空闲量相加。协调者的原 trial、正式轮、归档、解包和续跑目录要映射到实际设备；同盘合并计算，分盘分别检查。当前 C4 入口只接受这些目录同盘，发现分盘会拒绝，不能冒用单盘预算。Redis 内存保留 20%，元数据盘另计 AOF 增长和重写暂存。观测量覆盖准备、测量、排空和完整冷验，不能只用负载计时。

| 实验 | 峰值依据 |
|---|---|
| C1 | 用同参数试跑的对象写入和各盘峰值；64 MiB 应用 I/O 不能当对象存储占用上限，逐次 fsync、对象替换和后台清理都可能扩大占用 |
| C2 | 完整 trace 的实际准备、回放、排空、冷验增量，加观测和归档；不能只看 trace 压缩包大小 |
| C3 | 原文件数与 4 KiB 内容的完整导入实测；单独检查 inode、Redis、元数据持久化和每轮保留副本 |
| C4 | 父版本保留，新增 child、隔离修改、完整冷读，以及全程采样与归档；不能拿 JuiceFS 的短耗时代替 BrewFS 的观测时长 |

依据不足就不放行。清理完成不等于容量通过。旧 `capacity-check.py budget` 的“导入增量 × 副本数”只是一项输入，不能单独覆盖采样、归档或 C1 写入峰值。

## 本轮执行位置

- **A 组：** 当前 Off1 继续，不能清理。待子任务完成冷验、归档并真正退出，核对原父进程身份，再恢复原父，让它收取真实退出码、在第二轮停点结束并释放锁；不会自动恢复。此后才核对旧副本。C4 后续使用[逐轮续跑入口](C4-A-DIRECTORY-HOLD.zh.md)，每轮消费清理回执和清理后的容量快照，不再连续派发六轮。
- **B 组：** 保持停机。历史观测副本只占盘 0；即使全删，也不能证明另三盘够用。需要恢复 C1 时，先取回失败轮诊断、核四盘和依赖，确认回收后空间；新六轮从头校准，不混用失败批次的前两轮。
- **代码接入范围：** C4 逐轮入口已在本地接入上述检查，14 项相关离线测试通过，尚未部署。旧 C1/C2/C3 连续运行器没有完整的逐轮空间门槛，不应直接启动新的多轮批次；续跑前须加入同样的逐轮边界。文档不代表这些旧入口已经自动清理。

池中没有可运行任务时，确认没有活动负载和共享依赖后停计算费；保留盘仍计费。整池结束后，先核结果归档，再释放本轮新增实例和盘，保留原跳板、网络与 OSS 数据。
