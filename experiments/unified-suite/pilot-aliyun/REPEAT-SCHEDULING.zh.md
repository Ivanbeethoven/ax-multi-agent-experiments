# 按需服务器复跑手册：先排依赖，再开机器

> 历史协议，仅用于原冻结计划；新实验见[当前方案](../current/README.zh.md)。

给复跑 Agent。先读本批的 plan、inventory、SQLite 和资源账本。下面是调度规则；[历史试跑](PARALLEL-PILOT.zh.md)里的 IP、版本和费用不可直接照搬。默认只设 JuiceFS 外部对照；BrewFS 各方法和消融分开登记。当前小规模 C3、C4 派生为十万 × 4 KiB，C2 用完整 trace。

如果要让 C1–C4 本身同时跑，直接看[按实验分池的两池和四池排法](WORKLOAD-PARALLEL.zh.md)。

## 1. 选择机器和并行方式

| 情况 | 按需资源 | 怎么排 |
|---|---|---|
| 只有一条路线已准备好，或没有截止时间 | 复用跳板 + 1 个三节点池 | 先跑已就绪的队列；对照也可在同池分时跑。固定硬件、版本和冷启动规则；交替运行顺序，避免固定一方总在后面 |
| BrewFS 与 JuiceFS 都已就绪，且需要缩短日历时间 | 复用跳板 + 2 个独立三节点池 | A 跑 BrewFS，B 跑 JuiceFS。每池同一时刻只运行一个会消耗本池资源的任务；按 case、输入、轮次和配置配对。硬件资格须实测，报告保留池别 |
| C4 跨机流转 | 使用同一存储后端的源和目标客户端 + 该池 Redis、RustFS | 目标仅在 checkpoint 和接续验证就绪后启动。可借另一个已空闲的客户端，前提是拓扑、限额与版本匹配，且两个队列都为这次流转让出实际资源；否则按需临时加一台纯私网客户端 |
| 多 Agent 扩展或隔离 | 按该实验冻结的客户端数和每 Agent 限额申请 | 测试中的 Agent 并发由一个 cell 统一控制；不要用多个独立 cell 叠在同一后端冒充并发规模 |

一个试跑池的历史规格是客户端 **4C16G + 100 GiB PL1**、Redis **4C16G + 60 GiB PL1**、RustFS **8C32G + 4×60 GiB PL1**，Agent 限额 **2 CPU / 8 GiB，禁用 swap**。这是单台四盘 RustFS；若实验要求四节点，需另列四台对象机和真实磁盘成本，对照两边使用同样拓扑。协调者 SQLite 放本地独立盘；仅跳板有公网入口。开机前重新询价和盘点，不从历史规格推断库存。

## 2. 用依赖图排队，不按 C 编号串行

```mermaid
flowchart LR
    P["开机前：版本与产物、输入摘要、队列、询价"] --> G["池启动：角色、盘、限额和指标资格"]
    G --> A["A：BrewFS 就绪队列"]
    G --> B["B：JuiceFS 就绪队列"]
    A --> X["本池独占：资格 → 校准 → 正式 → 冷验 → 归档"]
    B --> Y["本池独占：资格 → 校准 → 正式 → 冷验 → 归档"]
    X --> H["交接：确认退出、释放租约、绑定证据"]
    Y --> H
    H --> N["同池下个就绪任务，或确认释放"]
    H --> M["C4 流转：源和目标同时就绪后开跑"]
```

- **开机前并行**：一处构建并冻结二进制和镜像；其他工作可以同步准备 trace 校验、配置、指标合同、盘容量和报价。就绪输入经同地域 OSS 内网或私网分发。未解决的发布、重挂写入、容量上限或模型接续问题先记阻断，不开池等修复。
- **开机后并行**：A、B 只在客户端、盘、Redis、RustFS 和采集器均独立时并行。目标是对照公平，不要求两边同一秒开始。禁止在计时池同时导入、归档压缩、跑另一项校准、清缓存或传大包；协调者上的归档若争用跳板带宽，也移到计时窗口外。
- **就绪优先**：C1 各 fio 模式按自己的输入和校准准入；C2 需完整 trace 与对应回放资格；C3 和 C4 派生各用独立 fixture，不以 C3 导入代替 C4。C4 流转另需会话 checkpoint 和源/目标资格。先安排能形成完整配对、无需等待产品修复的任务；消融只在对应主条件具备证据后排入。
- **失败可交接**：固定门槛未过就标记失败，保留校准与原始数据。只有证明 FUSE、进程、槽位和租约已关闭，才可将池交给不依赖该结果的任务；不能拿资源释放回执冒充正式验收。started 不自动重跑。

## 3. 每条任务都写清资源占用和交接

协调者从冻结计划和 `queues.json` 派发；每个池一个 owner。不同阶段的状态库如果指向相同物理节点，必须使用同一物理资源锁根；不能用两个 SQLite 文件绕开锁。共享同一 Redis 或 RustFS 的任务即使使用不同库、桶或路径，也登记相同的共享资源 ID。只读、轻量状态检查可并行；重读和压缩按实际磁盘及网络负载排队。

| 每条队列记录 | 必填 |
|---|---|
| 任务 | cell ID、arm、轮次、owner、前置条件和输入 SHA |
| 机器 | pool、实例和盘 ID、Redis/RustFS/采集器身份、槽位和配额 |
| 时间 | 计划启动窗；实际准备、校准、计时、排空、冷验、归档、释放确认的时间；计划值和实测值分列 |
| 交接 | 状态、原始包及 SHA、卸载及进程退出、租约为空、接手者、是否允许执行下一项 |
| 计费 | ECS、盘、跳板/EIP、网络、OSS；计费起点和确认释放时间，估算与实账分列 |

共用入口见 [并行配置](../12-parallel-baselines.zh.md) 和本目录的 [脚本索引](README.zh.md)。跨池接续应只消费核验后的交接回执；自动接续设置截止时间，超时后由协调者核实是否存在已启动的子任务。

## 4. 按资源小时决定是否加池

- **开机前算两份排程**：单池串行与双池并行。分别列每个池从创建到可释放的时长，把装机、输入导入、冷验、归档和等待交接都算进去。比较两份计划的完工时间与总成本：各池小时价 × 各自占用小时，再加共享资源和存储、流量。不要用整轮时长乘所有实例，也不要只按正式计时估费用。
- **第二池晚开、早收**：两条队列都有可以立即执行的工作，且节省的时间值得额外成本，才开第二池。示例：按历史报价 ¥4.566/小时，第二池从创建到释放占用 2 小时，估算约 ¥9.13；是否划算取决于单池方案也需要占用多久。当前报价另查。
- **提前排收尾**：最后一项通过或确认阻断后，先验原始包和远端读回，再用 `cloud.py release` 按本轮账本释放新增实例和随实例盘；查询实例和磁盘确认已释放，再给 `record-cost.py` 记计费终点。只停机或只提交释放请求不等于盘已停止收费。某池可单独释放；原跳板和已有 OSS 数据保留。若后续有确定任务，比较等待成本与释放后重建、恢复和重验的成本。
