# 64 / 128 Agent 扩展实验

**准备中，未购机、未部署、未开始测量。** 本方案将 64 Agent 设为主目标，128 Agent 为扩展目标。旧 9 台 / 最低 3 台安排保留为单臂资格与机制对照，不再作为整个实验的规模上限。C1–C4 是四个负责组，每组一个监督 Agent；被测的 64/128 个工作 Agent 与这四位负责人分开计数。

## 1. 场景、baseline、规模与指标

| 组 | 主实验 | baseline | 规模阶梯 | 核心指标 |
|---|---|---|---|---|
| C1 | 共享后端多 Agent：完整 trace 回放；真实 Agent 任务另测 | BrewFS Overlay + native lower vs JuiceFS；flat-v1 vs Overlay 单列消融 | 回放 1/8/16/32/64/128 Agent；消融 1/32/64；真实任务 1/8/32/64 | 完成任务/s、批次 makespan、逐任务墙钟与尾延迟、慢化比、公平性、操作/字节、失败率；客户端/元数据/后端 CPU、内存、网络、GET/RPC、排队与限流 |
| C2 | 海量只读 ML 数据发现/预处理/加载 | Pack packed-metadata-v3 vs BrewFS Native flat-v1 + TiKV | 800 万文件上 1/8/16/32/64/128 个隔离读取环境；固定 64 环境测 100 万/800 万/3200 万文件 | 文件/s、批次墙钟、访问延迟直方图、元数据 RPC/GET、缓存与空间；构建发布/普通导入成本单列 |
| C3 | 外置对象动态块在高并发下的延迟、读放大与容量 | 无 hint vs B=64 KiB/256 KiB/1 MiB/4 MiB；同版 RustFS、EC2+2 | 1/16/64/128 个在途请求；主池 128 GiB、对象 8 MiB+123 B；扩展 64/256 MiB+123 B 对象及 1 TiB 池 | 服务速率、p50/p95/p99、在途/排队、各层读取字节、实际 B/q、设备利用率与空间 |
| C4 | 批量 fork/clone，及有其他 Agent 持续工作时的跨节点流转 | F：BrewFS fork / JuiceFS clone / Native 全量 cp；M：BrewFS Overlay / JuiceFS，各有 stay/move | F：1/8/64/128 子副本，串行和突发创建分开；1M×4 KiB 与 400 GiB 混合文件树。M：1/16/64/128 活跃 Agent，迁移不同子集 | F：创建/首用延迟、总准备成本、空间、隔离；M：被迁移任务暂停/恢复、未迁移邻居 p99/吞吐变化、丢写/双写/会话完整性、move−stay |

Pack 只进入 C2，不加入 C1 通用读写或 C4 fork/流转。C3 的在途请求数不是 Agent 数；C2 扫描进程也不能直接称作真实 ML Agent。必须分别报告代理负载和真实任务。

### C1：两个回放口径与真实任务

- **弱扩展**：每 Agent 一个完整任务，N 增大时总工作量随 N 增加；报告吞吐和每任务慢化。
- **固定队列**：总计 256 个冻结任务实例，N 个 Agent 按固定派发顺序领取；报告批次时间、利用率与尾部。现有 7 份 trace 重复分配只能称任务实例，不能称 256 道不同题目。两次 Pytest 仍算同题不同采集。
- 每个 Agent 独立 workspace、HOME/XDG、会话与客户端缓存；可共享同一不可变基底，但必须核查所有写入隔离。**所有 Agent 访问本组同一持久服务池**，不能每 Agent 一套后端后再声称共享后端扩展性。
- 回放保留每份完整操作流、原写入内容与顺序；不把单条回放拆成并发操作。默认连续回放。可另开同条件的 LLM 等待模拟组，规则见第 4 节。
- 真实 Agent 使用冻结的 OpenCode、模型、任务清单、提示、预算和评分器。至少先冻结可覆盖 64 个任务实例的清单，独立题目数与重复次数单列；现有输入并未满足这个多样性要求。记录 API 排队、429、模型等待、工具计算和文件系统时间。真实模型组不叠加合成等待。

### 写入完成口径：主组同步发布，异步组单列

| 条件 | BrewFS | JuiceFS | 适用范围 |
|---|---|---|---|
| 主组与首次 C1 pilot | `cache.writeback_mode=upload_before_commit` | 客户端 `--writeback` 关闭 | C1 产品对比与消融、C4 默认写入 |
| 可选异步配对组，尚未就绪 | `cache.writeback_mode=commit_before_upload` | 客户端 `--writeback` 开启，`--upload-delay=0` | 先做 C1 独立资格，再预登记代表性任务与并发档位 |

这里比较的是数据映射发布与对象上传的先后，不表示每次普通 `write()` 都等待 S3。FUSE kernel writeback-cache 是另一项配置，保持原控制。异步组要求两边在本地暂存后允许提交元数据、后台上传对象；本地盘损坏风险、实际暂存持久性、容量背压与失败恢复分别核验，不凭开关名称假定保证相同。冻结并核实生效配置、上传并发、缓存/暂存预算和 JuiceFS 暂存阈值；read cache 上限不能冒充 dirty staging 上限。

异步功能必须在**相同 BrewFS 版本和 workspace 格式**下与同步模式配对。当前 `workspace-native-v2` 明确拒绝 `commit_before_upload`，正在单独实现；不只删除校验、不换成 flat-v1 来代表 workspace，也不因文档列出该组就宣称已支持。主矩阵 618/990 单元及现有运行脚本默认不变；异步组使用独立调度单、配置、run ID 和结果，暂不与 VM、LLM 等待等全部维度交叉扩增。

同一协调器记录三段：屏障放行至所有任务按合同完成必要 flush/close 的 **应用完成时间**；此后到全部任务的数据映射与对象上传完成得到确认的 **尾部 drain 时间**；两者之和的 **远端完成确认时间**。另报失败、dirty/staging bytes、待上传与 inflight 随时间曲线、峰值暂存空间及后台排队。确认采用轮询时记录间隔和确认开销，不把确认时刻冒充精确上传完成时刻。不能只用应用吞吐宣称远端持久吞吐提高。

先停止新增写入，核待提交、待上传、inflight 与失败/恢复队列均完成，再在不依赖源机缓存的独立客户端核内容。仅 `fsync/close` 返回或一个 dirty 指标为零均不是远端就绪证据；独立内容校验耗时另记，计时后执行，不能提前预热首读。若版本缺可靠的 drain/队列观测接口，该模式保持未就绪，不能用固定 sleep 替代。

- C2：只读计时前，Pack 发布和 Native 导入均须远端就绪；构建/导入与 drain 成本单列，不把异步上传混入读取成绩。
- C3：直接 S3 的请求完成与实际持久布局按原协议核验，不套用 FUSE 客户端 writeback 开关。
- C4 F：源树先远端就绪；创建返回与目标可用时间分别记录，全量 cp 也核相同远端可用边界。C4 M：checkpoint 后完成 drain、释放写者再在目标恢复；drain 计入暂停时间，stay 做同样流程。主组不自动开启异步，未来若测异步迁移须另立配对条件。

### C2 / C3 / C4 的扩展约束

- C2 已准备的只是 1,048,576 条记录。8,388,608 / 33,554,432 必须来自有来源清单的真实语料，冻结路径、大小分布、内容摘要和 ML 读集，不能复制同一批文件假称独立样本。固定 64 环境的 8M 条件复用同一实验定义，避免重复计数。先用 CPU 数据流水线，不把 GPU 训练时间混入文件系统指标。
- C3 先确认四开关和实际 external B/q，再测固定池上的请求并发；已有 s3_requests.py 是串行工具，**并发请求执行器尚待实现和资格验证**。128 GiB / 1 TiB 是应用对象字节，物理占用另外核算。4 KiB 是 Range 请求，不是新增 EC block 档位。
- C4 的 F 在 64/128 子副本条件增加 burst：单一屏障同时提交创建，资源限额不变；不能把串行创建乘除成并发成绩。400 GiB 树的文件大小/数量分布仍须冻结。F 和 M 不同时占本组服务池。
- M 冻结 `(活跃, 迁移)`：`(1,1)`、`(16,1/8/16)`、`(64,8/32/64)`、`(128,16/64/128)`。stay 也进行相同 checkpoint、释放写者、冷客户端恢复；同一轮保留相同数量的空闲目标环境，控制资源差异。邻居任务不停；与无迁移基线窗口比较。目的环境必须在另一节点，物理跨机另核宿主身份。

## 2. 一 Agent 一 VM / Docker

两种隔离方式是独立实验维度，分别建 campaign；先 Docker 完成主阶梯，再用 VM 复核 1/16/64，128 VM 作为扩展。生成器也可生成完整 VM 矩阵，但不要求无条件把全部维度做笛卡尔积。

| 配置 | Docker | 独立 VM |
|---|---|---|
| Agent 边界 | 一 Agent 一容器，独立 PID/mount namespace、workspace、HOME/XDG、会话与缓存目录 | 一 Agent 一 VM，独立 OS、挂载、目录与会话 |
| 工作负载预算 | 每 Agent 的 Agent 进程＋FUSE 客户端合计 2 vCPU / 8 GiB，禁 swap | 相同 2 vCPU / 8 GiB cgroup；参考 VM 4 vCPU / 16 GiB，OS 开销单列 |
| 参考执行节点 | 32 vCPU / 128 GiB，每节点最多 8 容器；剩余用于 OS/观测，实际利用率照实记录 | 每 VM 1 Agent；自备虚拟化宿主另算容量与预留，禁止 CPU/RAM 超卖隐藏竞争 |
| FUSE | 每容器核实际挂载与必要的 /dev/fuse/能力；也可用经验证的独立宿主挂载后 bind，仅在同一实验中统一 | 每 VM 核真实挂载、内核及限额 |
| 缓存含义 | 容器共享宿主内核；清客户端目录不等于清宿主页缓存；不在并发任务期间全局 drop_caches | Guest/宿主缓存分开记录；冷 Guest 不证明物理设备冷 |
| 身份证据 | environment_id → node/VM ID → physical_host_id（未知则 null） | VM ID 与物理宿主分开；阿里云未有证据时只称跨实例 |

不把 Docker 配成所有任务共享一个可写 bind mount。未核隔离、权限或实际预算时不发就绪屏障。每个真实 Agent 的模型凭据由批准的代理/机密注入渠道提供，不写进 trace 或公共结果。

## 3. 机器数和服务配置

每个 C1/C2/C4 服务池参考：RustFS 1 节点（32 vCPU / 128 GiB、基础 4×1 TiB 独立数据设备、单机 EC2+2），元数据 1 节点（16 vCPU / 64 GiB），协调/观测 1 节点（8 vCPU / 32 GiB）。客户端数增加时服务预算固定；服务扩容另开实验。Pack 即使较少使用远端元数据，也保留相同预算并报告实际使用量。TiKV/Redis 的实际进程数、拓扑与持久性须冻结；该方案不声称高可用或后端横向扩容。输入/缓存/元数据/结果盘、C3 请求节点和网络要求统一见 [HARDWARE](HARDWARE.zh.md)，基础 4 TiB 不是所有组的容量承诺。

| 资源组 | 64 Agent，Docker | 128 Agent，Docker | 64 Agent，独立 VM | 128 Agent，独立 VM |
|---|---:|---:|---:|---:|
| C1：G/A 顺序复用一池 | 8 执行＋3 服务＝**11** | 16＋3＝**19** | 64＋3＝**67** | 128＋3＝**131** |
| C2 | **11** | **19** | **67** | **131** |
| C3：2 请求节点＋后端＋协调 | **4** | **4** | **4** | **4** |
| C4：源/备用目标各一池＋3 服务；F 顺序复用 | 8＋8＋3＝**19** | 16＋16＋3＝**35** | 64＋64＋3＝**131** | 128＋128＋3＝**259** |
| 四组同时保留的 Linux 节点合计 | **45** | **77** | **269** | **525** |

这些数是提供/租用的 Linux 节点或 VM 数，不自动等于物理服务器数。C1 若同时做 G 和 A，需要额外一整池；BrewFS/JuiceFS 同时测也须复制独立服务池并做机器换位，不能同争一个后端。通常在同一池顺序随机化完成各臂三完整区组。

**分组顺序执行可复用资源**：64 Docker 通常按 C4 峰值准备 19 节点即可；其中 C3 可复用相应角色。9/3 台仍能做资格验证，但不能按本密度声称达到 64 Agent 主规模。自备强机可提高密度，须以另一密度条件冻结，并展示实际 CPU/内存、I/O、NUMA 与链路竞争。

F 的容量是独立硬条件：400 GiB×64 个全量子副本＋源约 25.39 TiB 逻辑数据；EC2+2 按 `2×逻辑数据/0.75`，保留总容量 25% 空闲，仅数据至少约 **67.71 TiB** 原始容量；128 子副本至少约 **134.38 TiB**。实测物理元数据、padding 和临时文件在除以 0.75 前另计，并逐盘检查偏斜。默认 4×1 TiB 后端甚至不能执行 8 个大树子副本（数据下限 9.375 TiB），须单独提供存储；不能删除 cp 对照。C2 按全量真实语料和两臂实测峰值配盘；C3 1 TiB 扩展默认一次保留一个布局池。具体计算与容量目标见 HARDWARE。

规划协议 v2 修正了“额外加 25% 容量”与“总容量空闲 25%”的差别，并补齐硬件目标和未验证项；原历史计划/结果不改写，条件数仍为 main 618 / expanded 990。

### 阿里云与自备服务器

- 阿里云：上述 Docker 节点可以是 ECS，独立 VM 模式每 Agent 一 ECS；私网业务和单一管理入口。冻结实例/云盘/带宽限制、型号、可用区、费用上限与精确资源 ID。实际资源清单确认前不购买。价格与库存执行前核，不引用旧单价预算。
- 自备：按角色交付实体机或 VM，提供可信 SSH/host-key、空闲设备/目录、资源限额和宿主关系。VM 创建、盘格式化、全局缓存操作需要提供方指定的权限范围，当前规划不授权执行。不能为凑数量偷偷租机器。
- 两类环境分别统计。节点异构时在同一硬件层内配对，不把不同环境合并成重复样本。收尾按各自归属保全/清理；自备服务器和已有数据保持由提供方管理。

## 4. 可选 LLM 等待：默认关闭，随机间隔、固定总量

仅合成多 Agent **trace** 回放可显式开启；直接性能测试、真实 Agent、C2 单纯扫描、C3 请求、F 创建不注入等待。

对一个逻辑任务确定 K 个已对齐的工具调用/Agent 轮次边界，指定总模拟等待 T：每段 `0 ≤ d_i ≤ 15 s`，`sum(d_i)=T`。须满足 `0 ≤ T ≤ 15K`。固定总量后，各段是相关随机分配，不能再称独立均匀分布。T 未指定不猜值，缺真实边界不按 FS 操作数或空闲间隔伪造。

同一配对任务的两个 baseline 复用完全相同计划和 SHA；同一 campaign 的逻辑 Agent ID 分开生成随机序列。跨 Agent 比较如需统一 T，必须不超过所有所用任务的最少边界容量。总墙钟＝实际回放＋模拟等待＋调度/工具开销；不强制令所有任务总墙钟相等。报告计划总等待、实测休眠、调度误差和扣除休眠后的回放时间；后者仍含解析与工具开销，不等于纯存储服务时间。

实现见 [THINK-TIME](../../tools/full-fuse-replay/THINK-TIME.zh.md)。现有 7 份 trace 的工具/轮次边界尚未逐份完成资格核验；这一组保持未就绪，普通回放不受影响。

## 5. 方法与统计

1. 冻结任务/语料/请求、数据完整性、二进制、镜像、服务配置和 placement；容量预检、初始化、下载/预热在计时之外。
2. 所有 N 环境健康、就绪、挂载隔离成立后，由一个协调器发屏障。记录应启动/就绪/实际启动/同时活跃/完成/失败数，以及实际 Agent、工具、I/O 并发曲线；分批达到 64 不算同时 64。
3. 一个单元是某条件下的一整个 N Agent cohort。各臂使用相同任务派发、初态、资源和种子；全体收尾保全后重建下一臂。区组内随机臂顺序，跨区组轮换物理放置。每条件 3 个完整配对区组，64 Agent 不是 64 个独立重复。
4. 持续记录每 Agent 的进度、I/O、工具/模型等待、CPU、内存、限流及后端排队；协调器计算 makespan，不跨机器相减 monotonic。各 worker 的阶段时间只在本时钟内相减。
5. 每 Agent 独立结果、操作/字节/句柄/最终树或任务评分；缺少任何结果都不得仅用最快子集汇报。容量或超时/故障按统一预注册规则记录，不把失败补成 0、不静默换小规模。
6. 大量条件先做资格，再逐阶段升档。升档检查的是完整性、容量、并发和观测能力，不以“BrewFS 必须更快”为继续条件。所有有效慢值保留。

主矩阵 618 个 cohort 测量单元，expanded 990（每个隔离方式各自计数，未加入可选模拟组）；**不是 990 个 Agent 或 990 个独立样本**。工具可按 C1–C4 单独生成，不自动依次执行。VM 复核可由调度单选择预注册子集；未选条件保持未运行。
