# 硬件预算与开跑验收

本页是 [规模方案](SCALE.zh.md) 的硬件合同。**节点数量已经核算；实际机器尚未验收，不能标成硬件充足或 ready。** CPU/内存参考预算有余量；C2 语料和 C4 大树复制需要独立扩容。规划生成器的 `hardware_verified=false` 不是漏填，而是等待实际证据。

## 1. 每个角色提供什么

| 角色 | CPU / 内存 | SSD 容量目标（系统盘另计） | 用途与限制 |
|---|---|---|---|
| Docker 执行节点 | 32 vCPU / 128 GiB | 输入 1 TiB＋缓存/临时 1 TiB，分开设备 | 最多 8 个 Agent，每个 Agent＋FUSE 合计 2 vCPU / 8 GiB；输入只读共享，写入目录隔离 |
| 独立 Agent VM | 4 vCPU / 16 GiB | 输入 256 GiB＋缓存/临时 128 GiB | 1 Agent，工作负载仍为 2/8；宿主不得超卖，另核 Guest 和宿主缓存 |
| RustFS | 32 vCPU / 128 GiB | 基础 4×1 TiB 独立数据设备 | 单机 EC2+2；这是基础池，不保证 C2/C4 大容量条件可执行 |
| 元数据 | 16 vCPU / 64 GiB | 1 TiB 专用数据盘起步 | 记录 TiKV/Redis 进程数、持久性、WAL、快照/压缩峰值；实测容量不足须在冻结前扩容 |
| 协调/观测 | 8 vCPU / 32 GiB | 2 TiB 结果区起步 | 日志、计数器、结果与校验清单；大语料的持久归档另计，不能假设全部副本能放这里 |
| C3 请求节点（2 台） | 每台 32 vCPU / 128 GiB | 每台 1 TiB 临时区 | 负载生成、内容核验与请求记录；128 在途请求不等于 128 Agent |

每节点另配至少 100 GiB 系统/工具盘。以上为容量目标，**不是已验证的云 SKU、IOPS 或吞吐保证**。同一配对区组的实际 CPU 型号、NUMA、磁盘性能限额、服务进程与版本一致；两臂按同一资源预算运行。

Docker 的 8×2 vCPU / 8×8 GiB 只占宿主 CPU/内存的 50%，余量用于 OS、观测和缓存。页缓存可能记入 cgroup；宿主有余量不代表 8 GiB 的任务不会 OOM。采集实际 `memory.current/peak/events`、`cpu.stat`、PSI、swap 和宿主 steal；OOM、任务限额节流与宿主争用分别报告，不能自动调大慢的一臂。

数据路径的共享节点（Docker 执行、RustFS、元数据、C3 请求节点）目标为 **25 Gbit/s 私网**。独立 VM 按实测单 Agent 峰值核链路，不能假定 4 核 VM 就有 25G。记录实际双向可持续吞吐、RTT、PPS、实例与云盘限速；资格阶段要求输入分发/日志链路的预计峰值不超过实测可持续能力的 70%。更低带宽另立硬件配置，不暗中合并。公网只用于管理，测量期间不从 OSS/公网逐事件读输入。

## 2. 总量与首次试跑

| 范围，Docker | 节点 | 参考 vCPU | 内存 GiB | 说明 |
|---|---:|---:|---:|---|
| C1 首次试跑：1→8→16 | **5** | **120** | **480** | 2 执行＋RustFS＋元数据＋协调；服务配置与正式组相同 |
| C1 或 C2，64 Agent | 11 | 312 | 1248 | 8 执行＋3 服务 |
| C3 | 4 | 104 | 416 | 2 请求＋RustFS＋协调 |
| C4，64 Agent | 19 | 568 | 2272 | 源/目标各 8 执行＋3 服务 |
| 四组并行，64 Agent | **45** | **1296** | **5184** | 约 5.06 TiB 内存；各组服务池独立 |
| 四组并行，128 Agent | **77** | **2320** | **9280** | 约 9.06 TiB 内存；扩展组独立立项 |

顺序复用四组时，64 Agent 按 C4 的 19 节点峰值准备，但 C4 的存储容量仍须另配。自备服务器的 vCPU 不自动等于物理核；必须提供真实核/线程、虚拟化分配和宿主关系。强机合并角色或提高容器密度要另立配置；不能只凑总核数而隐藏共机竞争。

首次 C1 只用完整 `pytest-full-02`，1/8/16 各做一个 BrewFS/JuiceFS 配对 cohort，属于部署与并发资格，不并入正式三个区组、不据此发布性能排名。16 个环境分在两台执行节点；先实现并验证就绪屏障与活跃曲线。完整 prompt 见 [C1 首次试跑](runbook/agents/C1-pilot.prompt.md)。该小 trace 的通过不能替代 Django、固定 256 任务队列或真实 Agent 的硬件资格。

## 3. 磁盘容量怎么算

统一要求：**每个实际卷在预计峰值后至少空闲 25% 容量，有限 inode 的文件系统也至少空闲 25% inode。** 不是给已用量乘 1.25；不只检查四盘总和，还检查偏斜最严重的盘。

EC2+2 的数据容量下限为 `ceil((2 × 逻辑数据字节 + 实测物理额外字节) / 0.75)`。额外字节包括对象/文件元数据、padding、版本/垃圾回收滞留、构建暂存、快照及压缩等峰值；已按物理字节测得的项不再乘 EC。若实测物理放大更大，采用更大值。分别核 RustFS、元数据盘和执行节点，不用一个总量掩盖其中一个盘已满。

| 条件 | 同时保留的逻辑数据 | EC2+2 数据下限，已留 25% 空闲 | 默认 4 TiB 原始池 |
|---|---:|---:|---|
| C4：400 GiB 源＋1 子副本 | 0.78125 TiB | 2.08334 TiB | 数据部分可容纳，额外项待核 |
| C4：源＋8 子副本 | 3.515625 TiB | 9.375 TiB | 不足 |
| C4：源＋64 子副本 | 25.390625 TiB | 67.70834 TiB | 不足 |
| C4：源＋128 子副本 | 50.390625 TiB | 134.375 TiB | 不足 |
| C3：单个 1 TiB 对象池 | 至少 1 TiB，按实际对象数向上取整 | 至少 2.66667 TiB | 额外项/对象取整待核 |

C4 的 64/128 大树条件以 **80/160 TiB 原始容量作为初始配额目标**，仍须把实测额外项代入公式；这不是对特定云盘规格或四盘拓扑可用性的承诺。若所选供应商/实例不支持该容量和拓扑，先修订并冻结整组相同的存储配置；不能临时拆成串行删副本、改布局或去掉 cp 臂。保全结果所需的全体副本在验收前都要计入峰值。

- **C1 输入盘**：7 份压缩归档合计约 9.69 GiB，但 Django 的单个 `events.jsonl` 就有约 21.36 GiB。按完整解包后实际占用和文件数核容量，不把压缩包大小当运行内存。只读输入可按每宿主一份复用；每 Agent 的工作目录、写入和缓存独立。流式解析，记录解析 CPU/RSS 和输入盘 I/O；不能将整个大 trace 读进每个 8 GiB cgroup。单机目录盘回放另记为负载生成器参考，不从被测时间中相减。
- **C1 缓存/临时盘**：规划每 Agent 磁盘缓存上限 64 GiB，8 个共 512 GiB；容器层、HOME/XDG、初态、输出、日志和未收集终态另计。实际缓存开关/上限必须冻结并检查生效。固定队列的 256 个任务要按峰值保留数计算，不能只按当前 N；不得在结果未核验前删除已完成目录来腾空间。新 trace 和真实 Agent 任务重新核算。
- **C2**：文件数不能决定容量。以 32M=33,554,432 个文件为例，均值 4/64/256 KiB 分别是 128 GiB / 2 TiB / 8 TiB 逻辑数据，数据下限分别为约 0.33334 / 5.33334 / 21.33334 TiB；这只是算术示例，不是已知语料分布。取得全量真实 manifest 后，分别测 Pack 和 Native+TiKV 的导入/构建、索引、对象与元数据峰值，按更大的一臂配盘。共享只读语料不乘 reader 数，独立客户端缓存和临时输出要乘。
- **C3**：默认每次只保留一个布局条件的对象池；前一条件数据/布局/结果保全后才按精确命名空间释放。若同时保留 5 个 1 TiB 池，数据下限就为 13.33334 TiB，基础池不足；不得暗中依赖前轮对象或覆盖其证据。
- **C4 M**：迁移阶段计入源、目标同时存在的缓存、检查点和暂存，standby 节点不是免费空间；F 与 M 顺序复用。

## 4. 怎样判定可以开始

负责人在本批 `hardware-readiness.json` 逐角色记录：实际资源 ID/宿主映射；CPU/内存/cgroup；每卷容量、free、inode、磁盘/实例限额；两臂峰值预算及计算依据；链路实测；输入、生成器、观测进程的资源消耗；缺项与 `verified=false/true`。**这里规定的是验收产物，目前没有自动端到端硬件验收器**；不得仅创建一个 true 字段代替原始证据。

已有 [host_preflight.py](../../bench/host_preflight.py) 只检查基础主机/挂载条件，其默认 8 核/30 GiB 判据不能证明本表的 32 核/128 GiB。使用其输出加实际只读核验，逐步命令按 [SCALE-RUN](runbook/SCALE-RUN.zh.md) 记录；[scale_plan.py](../../bench/scale_plan.py) 只输出目标、容量下限与未通过的验收项。

资格阶段发现输入盘、解析器、观测或共机干扰限制压测能力时，先保留记录，再统一修正两臂配置并重新冻结。正式阶段固定服务预算后出现的 RustFS/元数据饱和，是要报告的扩展性上限，不能自动扩容重跑或删除慢值；也不能未经归因便称为文件系统自身差距。

阿里云需进一步核当前 SKU/云盘/配额/带宽、实际费用上限和资源归属；自备机器需核设备、宿主关系及授权目录。尚无实际清单或预算时，只交付配置和缺项，不从旧实验借用实例、不自动采购。硬件验收通过只覆盖该批冻结的规模、输入和配置。
