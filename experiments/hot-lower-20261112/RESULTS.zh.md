# 热 lower Overlay 优化结果

2026-11-12，本机 WSL Ubuntu 24.04。没有启动云资源。
历史云上 35.5% 开销数据保持原样，以下均为新的本地测量。

## 实现

BrewFS 本地提交 `02d4b83e07c94d50bd913461f02bd89d99d84d8c`，基于核对时的
`origin/main`：`ca07159f3da4b670e4aeb878faef928e69bc1634`。

- `get_extent_deltas_bounded` 调用路径缓存已证实为空的上层区间查询。
- `packed_opendir_once` 缓存两层均无目录增量的结果；有目录项或删除标记时正常合并。
- 复用现有行缓存，最多 65,536 项并受 TTL 限制。键包含 workspace、租约代数、
  head/layer 身份与版本、inode 和区间。提交前后失效、版本票据与取消后的权限撤销
  防止旧空结果遮住新写入、截断、目录修改或新视图。
- 已认证 lower 帧保留预算为 8 MiB，两组相同，摘要校验未关闭。
  这是从旧补丁单独移植的共同底座，其收益不作为空查询缓存收益。

私有 workspace 可调同步的设计位于 BrewFS `doc/architecture/private-workspace-sync.md`：
默认远端确认；可选本地数据与日志落盘后返回，后台按条数、字节和时间合批，满额时等待；
fsync、发布、fork、迁移和卸载等待远端追平。设计包含 fencing、幂等重放和恢复要求。
**后台提交尚未实现，当前写入确认语义不变。**

## 热读耗时

每负载 7 对：run-03 三对，run-04 四对。初始三对中实际含上层数据的两个路径出现
约 7–10% 时延变化，因此补了四对；所有成功数据均进入汇总。每单元 128 轮，交换顺序。
表内为各单元总耗时的中位数，降幅为中位数之比。

| 负载 | 缓存关 | 缓存开 | 耗时降低 | 七对逐对降幅范围 |
|---|---:|---:|---:|---:|
| 原 13 B/64 B 两文件 | 704.6 ms | 455.5 ms | **35.3%** | 31.8–40.6% |
| 包含上层修改、删除与重命名 | 1438.8 ms | 1235.3 ms | **14.1%** | 3.2–28.6% |

每单元实际 FUSE 读取分别为 256 次/9,856 B、640 次/1,060,224 B。
28 个单元逐次核对内容与目录均通过，最后一轮预热与计时阶段 RustFS 请求数、收发
字节数均为 0，计时前后未完成请求数均为 0。

| 延迟，中位数 | 缓存关 | 缓存开 |
|---|---:|---:|
| 两文件 pread | 613.4 µs | 117.2 µs |
| 两文件打开并列目录 | 2596.6 µs | 1701.3 µs |
| 修改负载打开并列目录 | 3929.4 µs | 3916.3 µs |
| 上层修改文件 sub/edit.bin 的 pread | 878.6 µs | 893.7 µs |
| 上层新建后重命名文件 sub/renamed.txt 的 pread | 806.6 µs | 820.4 µs |

延迟先取每单元中位数，再跨七次取中位数。有上层数据的两个路径约慢 1.7%，
没有声称它们变快。修改负载的改善主要来自其余三个未修改文件的空查询复用；
有上层目录项的目录枚举时延基本相同。

## 实际少查了多少

下表为每单元计数，七次重复一致。首次填充发生在预热，命中次数只含正式测量。

| 计数 | 两文件：关 → 开 | 修改负载：关 → 开 |
|---|---:|---:|
| 上层区间查询 | 256 → 0 | 640 → 256 |
| 空区间缓存命中 | 0 → 256 | 0 → 384 |
| 上层逐层目录探查 | 512 → 0 | 512 → 512 |
| 整目录空结果命中 | 0 → 256 | 0 → 0 |
| Redis ZRANGEBYLEX，实测 | **1024 → 0** | **2432 → 1664** |
| Redis 全部命令，扣除采集 INFO | 3584 → 2048 | 9344 → 8576 |

一次区间查询覆盖两层；目录探查按层计数，空目录命中按整个目录计数。
有上层目录项时后续合并分页不在“探查”指标内。Redis commandstats 包含 Lua 内部
命令，不能直接换算成网络往返，也不能用上述两个缓存计数计算全局命中率。

两文件缓存开启后仍有 2048 条 Redis 命令：TIME 512，GET/MGET/MULTI/EVALSHA/EXEC/
STRLEN 各 256。源码中的 `packed_enumeration_fence` 仍读取最新 head 并验证读租约；
未将“零 RustFS 请求”写成“零远端元数据访问”。

## 混合读写检查

另用仓库现有 Compose runner 比较原版 release 与候选 release，一对 `fio-randrw`：
70% 读、4 MiB 块、4 jobs、每 job 512 MiB、io_uring depth=1、direct=0、20 秒、
固定 seed=20261112。总文件集 2 GiB。

| 指标 | 原版 | 候选 |
|---|---:|---:|
| 读写有效吞吐，包含运行和写回排空 | 230.29 MiB/s | 229.48 MiB/s（−0.35%） |
| 测量后排空时间 | 26 s | 39 s |
| 最终 dirty/pending 字节与操作 | 0 | 0 |

按时间运行，两组实际 IO 总量不同。候选活动阶段吞吐较高、随后排空较长；合并后
吞吐基本不变，不能只用活动吞吐宣称提高。两组均正常卸载。这里只做一对回归检查，
不据此推断完整吞吐或尾延迟曲线。Compose 对比器的对象账本缺失，原报告保留提示；
完整 RustFS 请求计数证据来自上面的热读实验。

## 正确性与记录

默认 workspace 测试 1,355 通过，Overlay 完整库测试 2,788 通过；各有 265/485 项
原有 ignored，本次未新增忽略。新增路径测试覆盖上层写入、hole、截断/扩展、
创建/重命名/链接/删除、删除标记、视图切换和失去本地租约权限；另检验容量、TTL、
并发失效和帧保留。格式、workspace check/build、两种 FUSE runtime、shell 检查、
默认及 Overlay 的全 targets Clippy 均通过。日志及一次额外重复编译中断见
[检查记录](evidence/checks/README.md)。HTTP 计量代理两项测试通过。

构建使用正常优化的 release。源码、补丁及二进制 SHA 见
[provenance.json](evidence/provenance.json)，原始命令保存在每轮 `run.json` 的 argv。
二进制在本地提交前构建，记录为基准提交加完整补丁；该补丁与随后提交内容一致。
没有将新 SHA 冒充二进制内嵌版本。可复用构建/检查脚本位于 BrewFS `tools/perf/`。

失败准备记录保留：run-01 代理环境丢失导致分支核对超时；run-02 桶名过长；
guard-p1-before 镜像没有 curl；guard-p1-before-r2 Windows CRLF shebang。
它们均未进入性能统计。历史数据未被覆盖或修改。

本机 RustFS 使用同一宿主的四个目录，不代表四台云存储节点。尚未验证跨机延迟、
大工作集、多客户端竞争、后台同步与崩溃恢复，也未测真实 agent 端到端收益。
本次证明 lower 已热时，重复的空上层查询可以复用，并减少该小负载的实际命令与耗时。
