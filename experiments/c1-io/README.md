# C1：对象布局与文件 I/O

**RQ：每对象 B/q 布局能减少多少读取放大，能否缩短文件 I/O？** 对应论文 Variable-Granularity Object Storage；同时测 Native Overlay 的常规读写成本。

配置：[experiment.json](experiment.json)、[fio-profiles.json](../../configs/fio-profiles.json)。主机为 A366，后台为四节点 RustFS 和 A355 Redis。每次一个挂载、4 GiB 总内存、2 GiB 磁盘缓存。BrewFS Native Overlay、原生 JuiceFS、JuiceFS Overlay 轮换执行。

| 类别 | 输入与操作 | 改变的参数 | 输出 |
|---|---|---|---|
| 主实验：fio | 32 GiB 初始数据；顺序读/写各 8 GiB；随机读 65,536 次；同步随机写 4,096 次；70% 读混合访问 16,384 次 | 五种访问模式，固定 8 个 job | 吞吐、IOPS、P50/P95/P99、CPU、S3 和磁盘字节 |
| 主实验：文件与目录 | 1 万/10 万个 4 KiB 文件；打开、属性、读取、分页列目录、覆盖、重复修改、重命名、删除分段运行 | 文件数 | 每段时间、操作延迟、元数据请求、缓存命中 |
| 消融：B/q | 4,096 次相同 S3 Range 请求 | B=64 KiB/256 KiB/1 MiB/4 MiB；同 B 下 q 开/关；请求=4 KiB/1 MiB | 实际 B/q、读取放大、每请求时间、EC CPU |
| 消融：文件路径 | 将同一 4 KiB 请求序列经过 Native Overlay | B=64 KiB/1 MiB/4 MiB | 应用请求如何形成 S3 Range，后端收益能否传到任务 |
| 消融：预读 | 与主实验相同的 4 KiB 随机读 | 三组关闭各自的数据预读，其余预算相同 | 前台时间、异步下载字节和退出前剩余时间 |
| 读写尺寸：随机 | 32 GiB 文件集合，8 个 job，每次合计读取或覆盖写入 256 MiB | B=64/256/1024/4096 KiB；应用请求=4/64/256/1024 KiB；纯读/纯写 | IOPS、带宽、延迟、上传完成时间、EC CPU、S3 与磁盘字节 |
| 读写尺寸：顺序 | 32 GiB 文件集合，8 个 job，每次合计读取或写入 8 GiB | B 四档；应用请求固定 1 MiB；纯读/纯写 | 吞吐、写入放大、编码成本、上传后尾部时间 |
| 每对象布局 | 256 个 16 MiB 对象；固定 4,096 个混合尺寸请求 | 按对象用途选择 B / 全部固定 64 KiB、1 MiB、4 MiB | 布局选择的总体收益、各类请求延迟、磁盘读取与写入 |

顺序请求为 1 MiB；随机读/写为 4 KiB；混合请求为 64 KiB。使用 `direct=1`、`psync`、`iodepth=1`、`verify=none`，内容直接比较另做。顺序写最后 fsync；同步随机写每次 fsync；混合写每 128 次写 fsync。job 使用独立区间，表中工作量为所有 job 合计。

目录组每目录 1,000 个文件：先列出所有目录、对每个文件 getattr、打开并读取完整 4 KiB，三段分别计时；再覆盖前 1% 文件、对前 100 个文件各重复覆盖十次、将下一组 1% 文件改名、删除另一组 1% 文件、创建 1% 新文件，每段结束 fsync 并记录上传完成。每个系统使用相同文件编号集合与内容，冷热读取分别从相同初态进行。

q 由 RustFS 根据 B 和 EC 2+2 布局选择。准备阶段读取实际对象布局并保存；每个 B/q 条件写入自己的对象。请求偏移表固定，包含四种边界起点及边界前 2 KiB 的位置。客户端块大小保持 4 MiB。

尺寸组使用 `direct=1`、`psync`、`iodepth=1`，关闭客户端数据预读，固定上传/下载并发。读写均使用相同的预分配文件集合；写入每累计 64 MiB 执行一次 fsync，最后 fsync 并等待远端可读。256 MiB 和 8 GiB 都是全部 job 合计，随机请求位置按种子生成。写入组每次从相同父版本重新派生，不把前一条件的修改带入下一条件。

同一个 B 下改变应用请求大小；同一个应用请求大小下改变 B。JuiceFS 和 JuiceFS Overlay 执行相同的 8 个随机条件与 2 个顺序条件，使用其实际对象布局并记录。两组对照结果可复用于四个 B 的图，不重复执行四遍相同对照。每个请求尺寸至少呈现读取与写入两张曲线。

每对象组将对象分成固定的三类：50% 为 4 KiB 随机读，25% 为 64 KiB 随机读，25% 为 1 MiB 顺序读；对象编号决定用途，三类分别请求 B=64 KiB、256 KiB、4 MiB。分配发生在写入前，所有条件使用相同内容与访问序列。完整对象上传、布局选择和后续读取分别计时。文件系统 `auto` 的实际选择单独记录，按用途指定布局的结果按该策略命名。

对象已有布局不会因修改进程参数自动改变；每档重新写入对象并读取持久化布局。保存 `requested_B`、`actual_B`、`actual_q`、对象逻辑长度、各分片长度和 EC 配置。q 开关实验使用对应的服务配置重新准备对象。

文件读取同时记录客户端冷态和同挂载第二遍的热态。物理读取放大使用对象后端冷态数据；后端热态另列。内容检查放在计时后，读取全部实际字节直接比较。

**工作量：17 个主条件、24 个消融条件、40 个读写尺寸条件，三次重复共 321 次系统运行。** 每次只运行一个计时条件。32 GiB 输入复用，准备对象与写入副本按条件清理；B/q 直接对象测试只运行 RustFS。

执行采用 [c1-execution.json](../../configs/c1-execution.json)：准备阶段最多两个任务并行，fio 条件内部固定 8 个 job；A366 测量时，A355 可用 2 个逻辑 CPU、2 GiB 内存解析上一条件的小结果或生成下一条件参数。后台处理使用 Redis 之外的 CPU，并计入主机现有预算。实际对象准备、读回和清理安排在计时窗口之外。记录 `schedule.jsonl` 和整轮墙钟时间，复用相同不可变输入及匹配的 JuiceFS 对照结果。

