# A355：Overlay 热读后续优化

本轮减少了打开/关闭文件时无用的异步状态和调度，没有减少或跳过一致性校验。两个文件和一万文件的三对测试均变快；32 文件结果波动，未证明稳定收益。

代码：[BrewFS 0844a9d](https://github.com/brewfs/brewfs/commit/0844a9d7b6516deb068ed13d3760e855ef4bbc3d)，已推送到工作分支，未合并。

## 总耗时

单位 ms，三对中位数。两种开销分别为 `新 Overlay / 旧 Overlay - 1`、`新 Overlay / 新版只读 lower - 1`。逐次结果、阶段耗时与计数见 [完整对照表](evidence/comparison.md)。

| 实际文件数、计时轮数 | 旧 Overlay | 新 Overlay | 新版只读 lower | 新/旧 | 新/lower |
|---|---:|---:|---:|---:|---:|
| 2 × 257 轮 | 930.342 | 852.654 | 660.415 | −8.35% | +29.11% |
| 32 × 257 轮 | 9082.011 | 8734.599 | 7583.807 | −3.83%（波动） | +15.17% |
| 10,000 × 3 轮 | 41779.133 | 40476.011 | 26521.586 | −3.12% | +52.62% |

新旧逐对变化：2 文件为 −2.41%、−4.08%、−21.19%；32 文件为 +17.59%、+2.36%、−9.86%；一万文件为 −5.35%、−2.97%、−2.38%。32 文件均值和中位数的变化方向不同，不能用其中的负数宣称收益。

所有热读计时段的对象读取请求、字节均为零。但一万文件组包含元数据缓存到期后的回填，**52.62% 不是所有缓存均命中时的固定 Overlay 开销**。缓存容量、TTL、输入、FUSE 参数均保持新旧一致：行缓存 64 MiB / 60 秒，payload 为小输入 8 MiB、大输入 64 MiB，FUSE 属性和目录项 TTL 实测为零。

一万文件的阶段变化如下，均为三次的算术平均值，不能与上表中位总耗时直接相加：

| 阶段 | 旧版 ms | 新版 ms | 新−旧 ms |
|---|---:|---:|---:|
| 文件 open | 24362.374 | 23590.476 | −771.899 |
| 文件 close | 3540.629 | 2882.189 | −658.441 |
| pread | 10530.815 | 10460.430 | −70.385 |
| 打开并列目录 | 86.935 | 84.951 | −1.984 |

## open 与剩余查询

独立诊断批次的 32 文件组，文件 open 平均 587.88 μs；服务端 FUSE OPEN handler 平均 23.92 μs。前者还包含路径 LOOKUP、内核通信与调度，不能把差值全部归到 Redis。

| 服务端阶段 | 每次平均 μs |
|---|---:|
| 句柄内存准入 | 0.51 |
| 获取打开所需属性 | 4.91 |
| 记录打开并检查权限 | 5.22 |
| 更新 inode/句柄表 | 2.13 |
| 权限缓存查询（已包含在权限阶段） | 0.79 |
| 权限解码（已包含在权限阶段） | 1.79 |

本轮没有进一步减少热读的 Redis 查询，原因已经分清：

- 2/32 文件的权限、空区间和空目录结果均命中缓存；上层区间/目录查询为 0。257 轮仍有 514 次 MGET：OPENDIR 建立一次目录视图，首次 READDIR 的 offset=0 再刷新一次。代码是 `packed_enumeration_fence`、`refresh_dir_handle`；保留刷新，才能看见打开目录后的修改。
- 一万文件的行缓存实际占约 31.03 MB，低于 64 MiB 限额。三轮累计各有 10,000 次上层区间查询、20,000 次空区间命中；两版均为 29,750 次 MGET、20,020 次 ZRANGEBYLEX。变化集中在缓存到期后的回填，后台命令另列。
- 控制诊断在第一遍读完后等待 61 秒，32 文件再次读取时，权限回填 8.89 ms、区间查询 13.30 ms；实际增加 101 次 MGET、66 次 ZRANGEBYLEX，**对象读取仍为 0**。大输入的回填与 60 秒 TTL 到期一致，不能归因于对象未热，也不能只凭容量推断命中。
- 会话续期不清空文件行缓存的回归测试通过。没有把 JuiceFS 的心跳失效疑点直接套到 BrewFS。

这些分段包含等待；权限子项不能与父项重复相加。原始分段、命令和每次 open/close 在 [诊断汇总](evidence/diagnostics-summary.json) 与压缩证据中。

## 修改与正确性

- 只有实际执行 O_TRUNC 或写回时才创建对应的大异步状态。FUSE OPEN 状态由 14,016 B 降至 3,264 B；VFS close 由 3,896 B 降至 536 B；FLUSH 由 3,768 B 降至 232 B。
- 干净只读 FLUSH 使用已有 `run_ready`，仍执行真实脏状态检查；遇到等待时，把同一个操作交给持有生命周期的任务。没有跳过脏数据、权限、版本或租约校验。
- 只读打开不再复制用不到的 layer vector。缓存容量和一致性规则未改。
- 首轮 fio 暴露连续版本变化耗尽旧的三次重试上限。现在只对明确的版本变化重试，共享 10 秒预算并退让；每次重取版本、使用私有输出，最终校验成功才交付。租约失效、损坏和后端错误仍失败，读操作不提交元数据。

主要 memmove 符号的 CPU 采样占比：路径 open 9.08% → 5.98%，openat 9.70% → 5.60%。这是诊断采样，不等于总耗时下降比例。

验证包括 KV/租约/权限/缓存/写回/驱动测试、默认及测量 feature 的 build/check/Clippy、两种 FUSE runtime 编译和脚本检查。并发替换 600 次、9,600 次内容读取；混合读写 59,796 次内容读取；全部重新挂载读回通过。连续五次版本变化、持续冲突超时和不可重试错误各有回归测试。

按本轮要求没有运行 SQLite；含 SQLite 的全量测试未执行。代码留在工作分支，不触发该全量 PR 工作流，也不合并 main。

## 混合 I/O 补测

5 秒测试没有 EIO，但 32 文件组的写入 P99 中位数高了约 32%，每单元仅约 200 次写入，因此保留原记录并补做三对 30 秒测试。两个阶段均使用 16 MiB 已写入并读回的文件、4 KiB 随机 I/O、70% 读、direct=1；进程计时包含最终 fsync。

30 秒结果如下；带宽单位 B/s，P99 单位 ms，均为三次中位数：

| 初始输入 | 版本 | 读/写带宽 | 读/写 P99 | 含最终 fsync 秒数 |
|---|---|---:|---:|---:|
| 2 文件 | 旧 | 274117 / 113146 | 80.216 / 3.785 | 30.945 |
| 2 文件 | 新 | 272737 / 112884 | 73.925 / 3.785 | 31.022 |
| 32 文件 | 旧 | 272438 / 111641 | 74.973 / 3.785 | 30.810 |
| 32 文件 | 新 | 269937 / 110288 | 79.167 / 3.949 | 30.833 |

吞吐中位数变化在 −1.21% 到 −0.23% 之间，含 fsync 的时间没有明显延长。32 文件组读/写 P99 分别 +5.59% / +4.33%；逐对读 P99 有升有降，不能宣称尾延迟改善。30 秒补测未复现短测的 32% 写 P99 增幅；更长时间的尾延迟稳定性仍未验证。每个单元的操作数、均值、P99 和命令见 [正确性及 fio 汇总](evidence/check-summary.json)。
