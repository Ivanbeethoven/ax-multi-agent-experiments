# AX 运行记录与工作区迁移协议

2026-10-23。**AX 集成和多 Agent 运行已具备，这是用户确认的当前状态；新对比实验尚未执行。**本文规定 T1–T6 的运行记录及 T5 的迁移步骤。sources.json 是历史源码审阅，不能据此否认当前集成。B0–B4 的组成和保存完成规则以 [baselines.md](baselines.md) 为准。

## 1. 运行记录与各实验的检查范围

每批登记实际 AX/BrewFS/基线版本、镜像摘要、节点与区域/可用区、CPU/内存/缓存、存储服务、输入摘要和任务清单。计划资源不是已部署硬件。每个工作区保存对应关系：

batch_id → task_id → AX actor → node/instance ID → workspace_id → mount/subvolume/volume ID → base_digest → checkpoint_id → writer_generation。

未采用的组件填 null；不同工作区不必有不同 StorageClass 或独立挂载。B4 额外登记 ESSD 卷 ID、可用区、容量/已用量、IOPS/吞吐配置、实例挂卷上限、XFS 版本及 阿里云 API request ID。共用卷保存“卷 ID → 全部工作区”的映射。

迁移前先固定下表，实际值随批次保存。不能从挂载目录数量推算独立存储客户端数量，也不能在看到邻居停顿后改用另一种挂载方式重算主结果。

| 测什么 | 怎么做、记录什么 |
|---|---|
| Agent 使用哪个工作区 | 列出 Agent、工作区、进程和所在节点 |
| 工作区使用哪个挂载 | 列出挂载、卷/子卷与共享该挂载的所有 Agent |
| 挂载对应哪个实际客户端 | 从服务端或客户端接口取得真实 client/session ID，并记录其对应挂载；无法查明就标为未知 |
| 哪个身份可以写 | 记录凭据引用或主体标识，不保存密钥；列出它能访问的工作区 |
| 撤销一次会影响谁 | 记录撤销对象、覆盖的客户端和全部 Agent；逐个检查邻居是否失去读写或被迫暂停 |

每 Agent 独立客户端与多个 Agent 共用客户端可以分别测，CPU、内存和会话数量也分别计入。Ceph 原生驱逐按 filesystem client 执行，会阻断该客户端访问 MDS/OSD；共用客户端是否连带影响邻居必须实测。[Ceph 官方驱逐说明](https://github.com/ceph/ceph/blob/tentacle/doc/cephfs/eviction.rst) JuiceFS 的旧写者处理方式尚未验收，不能假定它已有与 Ceph 相同的驱逐接口。

| 实验 | 该项检查 | 未达到时的结果 |
|---|---|---|
| T1 创建与容量 | 实际可用数、指定时限内有效读写、互不串写 | 拒绝、排队、超时是容量结果，保留超限组 |
| T2 修改、分叉、历史、回收 | 子分支含父任务已保存修改；父子独立；历史可恢复；回收不误删 | 区分初始基线克隆、父状态分叉、可恢复历史与已释放记录 |
| T3 发布共享 | 消费者绑定确切版本；半成品不可见；旧消费者不意外切版本 | 发布与读取失败保留，不阻塞无关实验 |
| T4 固定 16 个任务 | 相同题目、版本、预算和判题器，只变并发 1/4/16 | 全部指定任务进入结果，包括模型错误与超时 |
| T5 迁移 | 选中任务在另一节点继续；文件/会话正确；旧身份不能提交当前状态；邻居影响 | 不支持、失败、超时、正确恢复分列 |
| T6 机制 | 同接口、内容、缓存和保存规则，只改变指定机制 | 缺少等价开关时只作系统比较 |

源码的 Packed reader pin 有256个槽位；Entity持久owner是另一条记录路径，不能直接当作所有Entity或Agent的上限。部署版核验实际占用与限制后再选255/256/257边界。T1 的 N=16/64/256/1024、T2 的 H=1k/10k/100k 是**请求规模**。失败组不得跳过。分多个控制域时披露域数及全部资源，不写成单域容量；终止记录不充当可恢复历史。

**T1 容量组统一持有工作区。**在本组 t0 同时提交 N 个创建请求，t0+120 s 为准入截止。所有成功工作区保持打开、持有 owner/所需引用至 t0+180 s；在 t0+120 s、t0+180 s 分别核对可用数量、内容及引用状态，第二次核验后才统一释放。不能创建成功就 close 或释放 owner 来绕过容量限制。持续到达的创建压力组另跑：一个生命周期完成后才释放；后续请求仍按固定到达表到达，忙时排队，不等待上一条结束才发送。不把它的累计创建数当作同时存活容量。

任务完成由工具退出、内容检查和独立判题确认；AX Running、容器存活不是成功。日志外置，保留真实退出码。会话目录按实际镜像确认，不能只保存 /workspace 就默认包含会话。

## 2. T5 固定场景：64 个工作区，只迁 16 个

- 工作区编号 id=0…63，源节点固定为 node=floor(id/16)，即四个节点各 16 个。按冻结清单选中 16 个迁移对象，主线目标固定为 target_node=(source_node+1)%4；其他候选目标另作范围探测，不更换主线目标。
- 64 个工作区运行同一批冻结的文件操作脚本，不运行模型推理。全部在第 10 轮保存确认点进入短屏障；均已确认、现有工具均已结束后，协调器确定公共 t0。无法到达屏障者保留为准备失败，不静默更换任务。屏障前耗时和保存成本仍计入全任务时间，并在不迁移对照中采用相同屏障。
- t0 同时记录 16 个 migration_requested 和 pause_requested。迁移并发分别为 1、4、16；16 个选中工作区全部保持暂停，等到获得迁移槽位再记录 migration_started 并执行迁移，**排队计入暂停时间，等待期间不得继续写入或改变会话**。恢复时从同一个第 10 轮已确认状态续接。
- 48 个邻居在 t0 离开共同屏障继续工作，之后不发暂停请求；每 5 s 发出一轮请求，共 120 轮，计划时刻为 t0+5k s（k=0…119），持续观察 600 s。每轮期限为其计划时刻+120 s，不能因排队延后。t0+600 s 后不再发新轮次，最多收尾 300 s，收尾不延长单轮期限。
- 迁移恢复截止为 t0+600 s，整个配对批次截止为 t0+900 s，所有并发 C 和对照完全相同。未恢复、未完成和超时保留；若整卷操作中断邻居，照实计入。选中任务、邻居及全部 64 个的完成时间均与不迁移批次配对。
- 客户端总 CPU、内存和缓存固定。源/目标缓存状态分组；目标位置、迁移前后资源限制写入清单，不能因迁移而增加有效任务资源。

同节点重启只作恢复开销对照。跨节点必须有不同源、目标 node/instance ID。各工作区执行同一脚本到结束，不能用“迁移恢复很快但后续冷读取更慢”省略全任务代价。

## 3. 目标范围与云盘布局

预先列出候选目标：CPU 架构、镜像和任务资源条件相同，排除源节点；**不能先按某种存储能否挂载筛选分母**。同可用区、跨可用区分表。每个“工作区—目标—迁移方式”保存支持条件、是否实际尝试、状态是否正确和邻居影响；未知目标不算 BrewFS 可迁目标。比例定义见 [metrics.md](metrics.md)。

| 方案/布局 | 主迁移操作 | 必须计入或限定的条件 |
|---|---|---|
| B0 BrewFS | 按部署接口恢复选中工作区和会话 | 验证目标的网络、权限、元数据/对象服务和挂载路径；写权限移交与冷读计时 |
| B1 XFS reflink + restic | 保存确切 snapshot ID，目标恢复差异 | 允许复用已有基线；计备份、恢复、删除旧文件和校验 |
| B2 JuiceFS | 重挂既有远端工作区 | 计划迁移不强制新建 clone；记录缓存和旧写者处理 |
| B3 CephFS | 重挂原 subvolume | 不强制 snapshot clone；允许原生客户端驱逐，计入耗时 |
| B4 每 Agent 独立 ESSD PL1 + XFS 卷 | 只暂停该 Agent，正常卸载、detach、attach 同区目标，再挂载 | 不增加整盘复制或强制 snapshot；计 API 等待、限流、挂卷限制和配置资源 |
| B4 每节点一块 ESSD 卷 | 邻居继续工作时，使用运行前冻结的目录状态转移方案 | 目录不能独立 detach；整卷迁移单列，并记录全部邻居中断；reflink 不改变此粒度 |

真实云主比较在同一个 阿里云 可用区内同时测 B0 与 B4；不拿实验室计时与另一环境的云 API 时间混比。B4 按卷 ID 解析设备，核对 attachment 的实例与状态，不能仅检查 in-use；不会格式化原卷。

**跨可用区分产品和路线。**普通ESSD主组同区；Regional ESSD可跨区挂载/恢复，必须按支持地域、实例和故障语义另列测量；快照后新建卷另列，不混入原盘换挂结果。B0–B3也在同一候选清单上验证网络、权限、所有权和实际恢复，不预设任意区域都能迁。

## 4. 正常迁移：共同保存内容与步骤

操作需要的会话、工具输出、计划与预算放在工作区内，计入存储工作；额外实验采样日志才放在工作区外。64 KiB 合成 session.bin 只验证文件搬运，不证明原生 Agent 恢复。具体资格检查见 [Agent 状态调查](agent-trace-and-resume.zh.md) 与 [回放方案](replay-experiments.zh.md)。

所有方案保存工作区目录/权限/内容摘要、基线与保存版本、AX 会话、已完成工具序号与结果摘要、未完成操作、预算余量及任务/镜像/提示词版本。凭据由目标运行配置提供，不放 checkpoint。进程内存、活跃网络流和未确认外部事务不在恢复保证内；确定性脚本不产生外部非幂等副作用。

1. **调度与暂停。**主线全部工作区先在第 10 轮确认点记录 tools_quiesced 并进入共同屏障。t0 同时给 16 个选中者记录 migration_requested、pause_requested；它们保持暂停，获得并发槽位时记录 migration_started。48 个邻居在 t0 继续，主线排队者不得继续工作。
2. **保存状态。**第 10 轮已完成 checkpoint_started/confirmed：文件、会话、工具清单满足 baselines.md 的远端确认规则，共同完成记录已持久化。主线复用此确切 checkpoint，排队时不改变它，不为迁移重复制造一次任务写入；若迁移接口还需保存控制记录，其成本照常计入 t0 后暂停。第 10 轮保存及屏障成本保留在全任务计时中。
3. **释放源。**记录 source_release_started；关闭旧挂载或撤销旧写权限，取得对应证据后记 source_released。B4 正常卸载后 detach，确认 available 和 attachment；租约到期本身不能代替旧访问已撤销的证明。
4. **接入目标。**记录 target_restore_started；打开指定状态。B4 完成 attach、设备确认和 XFS mount。记 target_storage_ready，此时尚不算任务恢复。
5. **续接。**恢复会话和工具进度，完成预定必要内容核对后记 target_session_ready。确定性回放执行记录中的下一步；原生 Agent 恢复则由同一会话产生后续实际工具操作，不要求命令与未迁移组逐字相同。其结果通过预定检查才记 target_first_useful_result。touch、Pod Ready、额外预热 canary 均不算。
6. **跑完或失败。**原任务继续至 task_finished 并检查最终结果。任何一步失败记 migration_failed，保留阶段、原因和重试；重试仍属于原请求，计入其成本，不能默默重建空工作区。

关键事件由**同一协调器的单调时钟**记录指令发出或确认收到时间。主机本地事件只分解本机阶段，不相减两台主机的单调时钟。确认的网络时间属于端到端成本。协调器重启导致时钟域变化时保留原始事件，标记该时长不可计算，不拼接成正常样本。

B4 加记 unmount_started/completed、detach_started/completed、attach_started/completed、device_ready、mount_completed；跨区增加 snapshot_started/completed、new_volume_started/completed。分项可能重叠，不能直接相加替代实际经过时间。

## 5. 源故障、旧写者与结果检查

正常迁移与故障恢复分组。主故障范围仅为 Agent 工作节点不可用，远端存储保持正常；不能据此推断后端故障保证。

| 场景 | 操作和期望 | 结果证据 |
|---|---|---|
| 确认后源故障 | checkpoint 确认后不再写入，使源不可用；另一节点恢复同一状态 | 注入/检测时间、版本 ID、文件/会话/工具清单、最终任务结果 |
| 确认前失败 | 回到上一个已确认版本；未提供历史保存的方案明确记不支持此回滚 | 已确认/未确认操作、重做量；不得混成正常换挂结果 |
| 源隔离但旧进程仍活着 | 目标接管后旧身份尝试写文件并提交当前工作区状态 | 请求/返回、两端身份、目标读回、当前版本是否被污染 |
| 目标挂载或首次工具失败 | 不向后续工具暴露半恢复状态，按当前写权限决定重试位置 | 失败阶段、有效写者、重试和清理 |

旧写者返回测试按以下步骤执行，和正常迁移分开：

1. 先保存并确认一个版本，记录旧进程、实际存储客户端及写者身份。在未分区时验证源可访问数据服务。
2. 只断开源与协调器的链路，保留源到数据服务的链路，旧进程继续存活。保存实际过滤规则和探测结果；若部署不能分别控制两条链路，记为此场景未实现。
3. 让目标接管。记录检测、撤销或拒绝旧身份、目标取得写权限的时间及返回结果；不能仅凭一个“已隔离”布尔值判成功。
4. 目标写入并确认一份新标记；旧进程随后用旧身份写同一专用测试文件并同步，再尝试发布当前状态。分别记录本地写、同步、发布的返回值与时间。
5. 恢复协调器链路，旧进程再次尝试发布；目标及独立检查客户端重新打开指定状态并读回标记，检查文件和当前版本是否被旧写覆盖。同时检查未选中的邻居。
6. 旧进程只能改自己的本地缓存或独立旧目录、但不能污染目标当前状态时，单列这种结果；旧内容进入目标当前状态则为正确性失败。没有实际写入、发布及读回尝试的批次不算通过。

分别记录“旧文件写入是否拒绝”和“旧身份能否提交为当前工作区状态”。B1 旧本地目录可写不自动等于当前恢复状态污染；但协调器不再派发任务也不能证明旧进程不能提交。明确使用存储原生撤销、应用提交检查还是仅终止进程，并分别验证。B0 的 lease/generation 同样以实际拒绝与读回为证。

B4 正常迁移不要求先做 snapshot；主故障场景在保存确认后且未再次写入时使源不可用，让各方案恢复相同状态。源无法卸载、API 超时和卷长时间等待均保留。强制 detach 单列故障方式，并计文件系统检查/修复及内容检查，不用它改善正常迁移时间。任意时刻故障后精确回到旧版本，需各方案先提供相同历史保存保证，额外保存成本也计入。

所有损坏、失败、容量拒绝和邻居中断均保留。本阶段只准备实验与文档，不部署、不迁移、不注入故障。
