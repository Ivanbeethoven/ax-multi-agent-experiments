# Overlay 性能优化规划（基于 `2026-10-27` 磁盘矩阵与 ABBA 数据）

数据来源：仓库固定提交 `807ed09` 下 `experiments/aliyun-ai-trace/2026-10-27`（707 文件 / 5.5 MB 全量快照）。
文中每个数字都来自该快照的 CSV/JSON，不手抄。

## 0. 这批数据排除掉了什么（先做减法）

| 被排除的假设 | 证据 | 结论 |
|---|---|---|
| **磁盘太慢** | 磁盘校准：PL1 4 KiB 随机读 27.3k IOPS = 100 GiB PL0 的 **8.9×**；顺序 356 vs 127 MiB/s | overlay 只用 575→561 s（**−2.4%**）⇒ **不是数据盘瓶颈**，调盘无效 |
| **Redis 命令发太多** | packed 命令增量 **−40.3/−38.7/−40.0%**，回放却 **+14.2/+16.3/+14.8%** | 命令数**不是**解释变量；追「减少命令数」方向错误 |
| **C4 已经解决大头** | C4 vs 原版 1,621→561 s（2.89×，−65.4%） | **单次观测、C4 先跑、未清页缓存、无交叉** ⇒ 不能当因果；剩余 9–18× 仍在 |

**所以下一步不该做的事**：换盘、加 IOPS、继续压命令数、把 C4 的 2.89× 当已完成的收尾。

## 1. 剩下的候选，按「能否解释 9–18×」排序

### P0 —— 有效 FUSE TTL（`#364` 已立项，仪器是硬伤）

**为什么排第一**：输入里 **getattr 占 90.90%（1,588,057 / 1,747,109）**。
`src/fuse/mod.rs:66` 的 legacy policy 用 `BREWFS_CACHE_TTL_MS` 默认 **1 s**；`:3772` 的 writable ACL policy 用 per-mount TTL 默认 **0**。保存的 driver 对两者都写 `fuse.cache_ttl_ms: 0` 且不设环境变量 ⇒ **若无声明的环境覆盖，native 1 s、overlay 0 s**。

**量级估算**：158 万次 getattr，若 native 被内核缓存吸收而 overlay 全部穿透到用户态，哪怕每次只多 100 µs，也是 **158 s** —— 同一量级于观测到的 500–560 s。

**硬伤**：`src/vfs/stats.rs` 声明了 `fuse_getattr_ops` / `fuse_getattr_lat_us`，但**全仓没有更新点**，导出的 0 不能证明没有流量。

**动作（进行中，`issue-364-p0` agent）**：
1. 接通 getattr 计数与延迟（含测试）
2. 让实际发给内核的 `attr_valid` / `entry_valid` 在运行时可见（**只加观测，不改默认行为**）
3. 判别实验：native 在 `BREWFS_CACHE_TTL_MS=1000` vs `=0` 两点，记录**用户态次数 / 内核 FUSE 次数 / 耗时**
4. 判据：若把 native 也设成 0 之后差距明显缩小 ⇒ TTL 是主因；若不缩小 ⇒ 转向 P1

**验收**：同一份 1,747,109 次操作的 trace，读写字节一致、句柄归零；TTL 两点的差异必须能在**内核 FUSE 请求数**上看到，而不只是耗时。

### P1 —— close / flush 尾巴（图 4 已经指出，但还没人查）

**证据**：等量写 ABBA 里四项命令墙钟差异都在 **±1.1%**，**但**顺序写的 close 总耗时 **1.26 → 3.58 s（×2.84）**、**4.25 → 6.19 s（×1.46）**。

**含义**：写延迟看起来没退化，**收尾成本翻倍**。这正是「只看 write 延迟会漏掉」的那块。1,588 万次 getattr 之外，`flush` 12,675 次、`release` 10,595 次 —— 次数不多但**每次可能等后台排空**。

**动作**：
1. 给 close/flush/release 打三段计时：进入前、等待 writeback 排空、返回前
2. 记录**每次 close 实际排空的字节数与对象数**
3. 判别：把 writeback 关掉（牺牲持久性语义，仅作诊断）看 close 时间是否回到 native 量级

**判据**：若 close 的 ×2.84 全部来自「等排空」，那它是**语义代价**不是缺陷，应写进论文；若部分来自**串行化**（一次只排一个对象），那是可优化项。

### P2 —— 每次操作的固定开销（不是命令数，是命令**延迟**）

**证据**：packed 命令少 40% 却慢 14–16% ⇒ 单命令延迟或串行等待在变。

**动作**：按 `#364` P1 的清单打点 —— batch size（上限 64）、每阶段后端 await、gate 等待/持有时间、扫描行数、空 lower 扫描次数、冲突次数、upload 与 final-flush 等待。
**不要**把嵌套 Lua 的 commandstats 相加当关键路径。

**判据**：能给出「一次 mutation 的端到端时间如何分配」的一张堆叠图；各段之和与总耗时的偏差 <10%。

### P3 —— 重复目录合并（opendir 7,789 次 / readdir 7,757 次）

overlay 每个新 handle 都重建上下两层扫描并合并；native 可复用完整 listing。
`src/fuse/mod.rs:1381` 的 readdir 在 offset 0 时还会再触发一次 `meta_opendir`，不区分首次读与 rewind。

**动作**：按目录统计 open/refresh 次数、页数、合并行数、扫描与合并时间。
**判据**：若「同一目录在一次 open 内被重复合并」占 opendir 总时间 >20%，先消除这个已证明的重复工作（保留 whiteout、权限检查、rewinddir、rename 可见性）。

### P4 —— 缓存重填与读计划（`#364` P2）

在 overlay 侧 Inode/Dentry/Permission/Xattr 行缓存已有 lease 证明的前提下，打点：按 key 类型的命中/未命中、失效/过期/禁用原因、被丢弃的重填。读写路径分别统计精确区间计划命中、扫描/返回 extent 行数、压缩代次重试、upload barrier 等待。
**判据**：能说明「缓存命中率提升 X% 对应耗时下降多少」，而不是只报命中率。

## 2. 执行顺序与理由

```
P0（TTL + 仪器）  →  如果差距缩小 >50%，TTL 就是主因，先修策略再谈别的
        ↓ 否则
P1（close 尾巴）  →  图 4 已指出 ×2.84，是最可能被忽略的真实成本
        ↓
P2（阶段分解）    →  拿到端到端时间分配，才知道下一个该动哪
        ↓
P3 / P4           →  在 P2 的分解里占比 >20% 的那一项才值得动
```

**不要并行开五条线** —— 每条都要跑同一份完整 trace（每格约 560 s + 初始化），并行只会让归因更糊。

## 3. 每条优化的验收门槛（统一）

1. **同一份 trace**：1,747,109 次操作，读 281,774,624 B / 写 194,706,661 B，句柄归零
2. `performance_accepted` 与 `valid` **不得倒退**；probe errno 差异不得增加（当前 BrewFS 1,048 项）
3. 混合读写、close/flush/排空、正常卸载三组门禁都要过
4. **同主机交叉**（B–C–C–B），不再用「先跑 C4 后跑原版」的单次比值
5. **清宿主页缓存**，或至少在报告里标注未清
6. 报 **min/median/max** 与 n，不只报一个数

## 4. 这批数据本身的缺口（写论文前必须补）

- 每格 **n=1**，ABBA 才 2 次会话 ⇒ 无置信区间，图上的倍数只是描述性比值
- 全部 `performance_accepted=false`、`valid=false` ⇒ 工作量完整 ≠ 严格正确
- 三台 CPU 混杂（8575C / 8475B / 8575C）、顺序执行、未清页缓存、日志落盘位置不一致
- `#364` 的 TTL 假设**仍未闭环**（P0 正在做）
- packed 的 +14–16% **尚未归因**（P2 是唯一能拆开它的手段）
