# C3：共享训练数据与 Packed

**RQ：Packed 联合索引能否减少重复元数据访问，其准备成本需要多少次复用才能收回？** 对应论文 Packed Metadata；fork/clone 同时观察共享版本的创建成本。

配置：[experiment.json](experiment.json)。Packed 用于只读、反复使用的大量小文件数据集。比较 BrewFS Packed、原生 JuiceFS、JuiceFS Overlay。输入为同一份 4 KiB 小文件目录，每目录最多 1,000 项。内容按固定整数种子生成。训练数据版本保持只读，任务输出及修改进入私有可写层。

| 类别 | 输入和规模 | 计时与指标 |
|---|---|---|
| 主实验：准备 | 1 万/10 万/100 万文件，8 个准备 worker | 从本地完整目录开始，包含扫描、属性、构建、上传、注册/封存，到其他机器可读；记录各段时间、文件/秒、请求和峰值空间 |
| 主实验：加载 | 10 万文件，1/32/128 个加载任务，各自 shuffle，连续读三遍 | 首批 64 文件、每遍时间、总完成时间、元数据请求、S3/磁盘字节 |
| 主实验：派生 | 1 万/10 万文件，16 个子工作区，每个修改 1% 文件 | 父版本准备、fork/clone、挂载、首次读、私有写、空间增量 |
| 主实验：复用 | 10 万文件，每轮 32 个任务，连续 16 轮 | 同一次准备下第 1、4、16 轮的累计时间，确定准备成本何时收回 |
| 消融：整包缓存 | 10 万文件、32 个读者，关闭 `BREWFS_PACKED_CACHE` | 元数据和数据的整包下载对耗时、流量和尾部等待的作用 |
| 消融：解码保留 | 同上，retained payload=0 | 已解码帧复用的作用 |
| 消融：元数据缓存 | 同上，metadata cache=0 | 已读取索引/记录缓存的作用 |
| 消融：元数据表示 | 同内容对象、相同访问，Packed 索引与 KV 查询 | 联合索引页对数据库请求和读取时间的贡献 |
| 消融：表示与缓存组合 | KV 表示同时关闭元数据缓存，和上面的两种表示、有无缓存组成四组 | 区分联合索引与缓存保留各自的贡献 |
| 消融：同机共享缓存 | 10 万文件、32 个读者；同主机的只读版本相同，缓存总量相同 | 共享元数据、Pack、数据块对首遍下载和多任务读取的影响 |

配对比较每次只改变一项；表示与缓存的四组组合见 [ABLATIONS](../../docs/ABLATIONS.md)。缓存总预算和其余参数保持不变。表示消融使用同 payload 的 KV 适配；整包、解码保留、元数据缓存分别控制。

只读训练集允许 JuiceFS 直接共享目录，输出写到独立工作区。派生实验才创建可修改的 fork/clone。准备的全部必要步骤计入总墙钟，额外的实验内容检查单独计时。

每次加载有 2 个读取线程、batch=64。各任务的 shuffle 种子在系统间相同；首遍与后两遍分别呈现。派生后检查父内容不变、兄弟隔离与重新挂载读取。异步下载直到正常退出前的字节与耗时也保留。

**工作量：9 个主条件 + 6 个消融条件，三次重复共 105 次系统运行。** 100 万文件、128 个读者为一个独立扩展条件，共 9 次；先按实测占用检查容量。

```powershell
python -m bench.cluster.plan --group C3 --out runs/c3-plan.json
```

每工作区使用 4 GiB 配置，整包缓存是磁盘预算，解码保留是内存预算。全部容量、池和每挂载并发见 [MOUNTS](../../docs/MOUNTS.md)。
